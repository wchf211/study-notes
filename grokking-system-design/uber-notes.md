# Uber — 提炼笔记（132–137，2026-10-06）


## 132. 开场
- 按路线图走：需求 → 高层 → 详细 → 支付与反欺诈 → 评估——面试官期待的顺序。

## 133. 需求与估算
- 功能：司机位置 4 秒上报、找附近司机、叫车+通知最近司机、行程起终点支付、ETA、确认上车、双向实时更新、结束行程、push。
- 非功能：HA、可扩展、可靠、**强一致**（一单只有两个人看，必须看到同一状态）、反欺诈。
- 估算（5 亿乘客/2000 万 DAU，500 万司机/300 万 DAU，日 2000 万单）：
  - 存储 **2.71GB/天**（约 1TB/年）：乘客 500GB、司机 5GB、位置 108MB、行程 2GB/天。
  - 带宽 **114.2 Mbps**，大头是 4 秒位置上报（300 万×19B/4s）。
  - 服务器约 **360 台**（2300 万 RPS 代理 ÷ 64K）。

## 134. 高层：7 个 API
- updateDriverLocation、findNearbyDrivers、requestRide、showETA、confirmPickup、showTripUpdates、endTrip。
- 细节：updateDriverLocation 带**旧+新**两组坐标——服务端算轨迹便宜，丢点时能重建路线。
- **位置服务器与 web/应用服务器分离**：高频位置流量和行程请求流量隔离。司机拒单自动找下一位（内置可靠性）。

## 135. 详细：两层新鲜度（本章明星）
- 朴素做法（每 4 秒改 quadtree：删旧区+插新区+超阈值分裂）写放大太大 → **两层**：**hash 表存最新位置（4 秒更新）**，**quadtree 批量 10–15 秒刷新**。
- DB 按访问模式选：**Cassandra** 存司机最后位置 + 已完成行程（append-only，永不改，海量增长）；**MySQL** 存进行中行程（关系型、频繁更新、跨表一致）。真实 Uber 后来迁到 **Spanner**（全球事务+强一致读+自动多活）。
- 容错：主从同步复制 + 提拔。**Redis hash 当写缓冲**（扛约 100 万司机上报再批量落盘）；CDN 只放静态，实时数据走 **WebSocket**（不可缓存）。
- ETA：路网分区 + **contraction hierarchies** 预计算分区内最优路，只处理分区边界——每分区约 1 秒则整体约 1 秒返回，而非全图 Dijkstra。ML 升级：DeepETA（路由基线 + 残差模型）。

## 136. 支付与反欺诈
- 支付 correctness 第一：防漏付、重复付、金额错、币种错、悬空授权。**复式记账**保账实相符。
- **Auth-capture 两步**：叫车时风控过 → 预授权（PSP 网关）→ 行程结束真扣。
- Kafka 管线：creator（行程结束发钱移动元数据）→ processor → intent → PSP 执行 → writer 落库（借 Kafka 的 pub-sub+持久+异步）。
- 反欺诈按**时间尺度**分层：行前风控筛、行中实时、结算后复盘。欺诈手法像 zero-day 一样进化 → **ML 异常检测 + 人工审计**。
- **RADAR**（人机结合）：时序分析 → 生成拦截规则 → **分析师审批** → 实时拦截未知欺诈 → 反馈重训模型。人工审限制横向扩展，但降误杀。

## 137. 评估
- 一致性论证是亮点：**每单的写者/读者集极小，一致性成本不随车队规模涨**，所以强一致用得起。
- 可靠性小技巧：**手机当本地存储**，断网行程继续。
- 三句话收尾：quadtree 找司机、路由+ML 算 ETA、反欺诈保业务。

## 自测 4 问（带答案要点）
1. 司机位置 4 秒更新一次，quadtree 为什么不每次都更新？
   → 每次更新要删旧区+插新区+可能分裂，写放大太大；正解 hash 表存最新（4s），quadtree 批量 10–15s 刷新。
2. Cassandra 和 MySQL 在 Uber 里各存什么？
   → Cassandra：司机最后位置、已完成行程（append-only）；MySQL：进行中行程（频繁更新、要关系一致性）。
3. 支付为什么用 auth-capture 两步？Kafka 管线里谁干什么？
   → 预授权锁额度，行程结束真扣；creator 发钱移动元数据 → processor → intent → PSP 执行 → writer 落库。
4. 为什么这里敢用强一致？
   → 每单的写者/读者就两个人，一致性成本不随车队规模涨。
