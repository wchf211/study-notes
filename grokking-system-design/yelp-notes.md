# Yelp — 提炼笔记（127–130，2026-10-06）


## 127. 开场：proximity service
- 连接消费者和本地商家；核心难题是对数百万地点做**延迟敏感的空间过滤**——全扫太慢，先用空间结构（quadtree/geohash）缩小搜索范围。
- 读多写少（搜 >> 写）。

## 128. 估算（1.78 亿用户 / 6000 万 DAU / 5 亿地点）
- 功能：双角色账户（商家加地点、用户搜）、按名/GPS 搜、评价（文本/图/评分）。
- 非功能：HA、可扩展（**午餐高峰+旅游季** spike）、地点/评价/图片数据一致、低延迟搜索。
- 服务器：6000 万 RPS ÷ 64K/台 ≈ **93.75 万台**（DAU 当 RPS 代理的老套路）。
- 存储分项算：地点 5 亿×1296B=648GB；照片 5 亿×280B（blob 的元数据/链接）=140GB；评价 100 万/天×537B → 10 年约 **1.97TB**；用户 1.78 亿×264B≈47GB；共约 **835.5GB**。
- 带宽：每次搜回 20 个地点 × 3MB 照片 → 出 **331.2 Gbps**；入仅约 51Kbps——照片主导 egress。

## 129. 架构
- API 三个：list places、get place details（含评价/图）、submit review。
- SQL 存地点记录；blob 存照片（**PlaceID+timestamp** 做 key）；review 表存评分。
- 链路：user → LB → web/app → **search servers（读写流量分离）** + place servers；geocoding 用第三方（别自己造轮子）。

## 130. 空间索引（本章心脏）
- 朴素：世界切 **5×5 英里**格子，每格 ≤500 地点，KV 存（segment_ID → 地点列表）；陆地约 600 万格 → 索引约 **4.05GB**。多格半径搜索：圈定格子集 → 合并邻居 → 算距离。
- 静态格子死于**密度不均**（曼哈顿 vs 郊区）→ **QuadTree**：节点超 500 地点就四分；**叶子双向链表**串起来找邻居。
- 树多大：每地点 24B（PlaceID+lat+long）× 5 亿 = 12GB；内部节点指针约 10.7MB；共约 **12.01GB——单机放得下，索引不是瓶颈**。
- 分区：**region-based 被否**（旅游季热门地区成热点）→ **PlaceID 分区**（KV 映射 PlaceID→server）+ 热门地点缓存；按年 20% 增长规划。
- 可用：QuadTree 多机复制；KV 存（server→地点列表）让重建丢树很容易。新地点：写 DB + 写树，找段，超了就分裂。
- 排序：rating calculator 算总分（存 DB 和树）；树返回半径内 top 50–100 候选；aggregator 挑最终展示。**评分每天低峰刷一次**——频繁重写 tree/DB 太贵。

## 自测 4 问（带答案要点）
1. 静态网格分段有什么问题？QuadTree 怎么修？
   → 密度不均（曼哈顿 vs 郊区）；节点超 500 地点就四分，叶子用双向链表找邻居。
2. 为什么不用 region-based 分区？
   → 旅游旺季热门地区成热点；改 PlaceID 分区 + 热门地点缓存。
3. 整个空间索引多大？说明什么？
   → 约 12GB，单机放得下——索引不是瓶颈。
4. 评分多久刷新一次？为什么？
   → 每天低峰刷一次；频繁重写 tree/DB 太贵。
