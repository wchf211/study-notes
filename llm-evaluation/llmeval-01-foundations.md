# 评估地基（Ch1）：为什么 benchmark 不够、怎么看 trace

> 核心论点：榜单分数是给模型排座次的，不是给产品验收的。产品评估从 trace（完整执行记录）开始。

## 1. Benchmark 为什么不够

**Benchmark（榜单基准）**：公开标准化测试，给模型在通用任务上排名。问题：**平均数掩盖方差**——总分 85% 的模型，在你的 workload 上可能 40% 挂掉，某个关键子任务全灭。

例：客服 bot 通用知识榜单满分，但真实工单一半答错——因为工单依赖公司自己的政策，公开榜单根本不考。

铁律：**先定义"对你的用户什么叫 work"，再围着它建 eval**。eval 是找"修哪里"的工具，不是汇报的分数。新模型/新 prompt 上线必重跑——"更强"的模型可能在你的任务上回归。

## 2. 三层评估，各管各的

按真实度/成本排三层，**故意全跑**，各 de-risk 不同的东西：

1. **Unit tests（单元测试）**：确定性断言（"返回必须是合法 JSON"），便宜快，部署前跑。
2. **Model/human eval**：判断质量。**LLM-as-judge**（第二个模型按 rubric 打分——便宜可扩展，但 judge 自己要先被验证，它有 bias，比如偏爱长答案）；**human preference**（真人评哪个好——主观质量的金标准，慢而贵）。
3. **A/B tests**：线上真实用户对照——最真实，赌注也最大。

prompt 一改可能单元测试全过、用户听着别扭——只有 judgment 层抓得到；反过来只有 A/B 知道用户真选哪个。**跳过贵的那层，等于把 subtle 的质量回归放进生产**。

## 3. Trace + Error Analysis：修机制不修症状

**Trace**：一次执行的完整记录——每个输入输出、tool 调用、模型调用 + timestamp/latency/token 数/模型版本。理解成 AI 请求的**分布式 trace**：不只看到结果，还看到每一步怎么来的。

**Error analysis**：抽样 trace 标 pass/fail → 找到每个失败 trace**第一个出错的点** → 按失败类型归类计数（taxonomy）。

例：checkout bot 的 tool 调用返回了截断 JSON → 助手没拿到退款详情开始编 → 用户炸。表面是答案烂，**第一个错是 tool 调用处理**，修那——不是改 prompt。

要求：trace 必须**完整**（system + user 全要）且人类可读——残缺的 trace 比没有更坏（看着可信，关键一步没了）。
**先做 error analysis 再设计 eval**——taxonomy 直接告诉你 eval 该查什么。

## 自测 4 问（带答案要点）
1. Benchmark 高分为什么不能作为上线依据？
   → 平均数掩盖方差；在你的 workload 上可能关键子任务全灭。
2. 三层评估各抓什么？为什么故意全跑？
   → 单元测试/判断层/A-B；各 de-risk 不同东西，跳过贵层=放回归进生产。
3. Error analysis 的三步？为什么找"第一个出错的点"？
   → 标 pass-fail/定位首错点/归类计数；修机制不修症状。
4. Trace 不完整为什么比没有更坏？
   → 看着可信但丢了决定性步骤；误导 debug 方向。
