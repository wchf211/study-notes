## 1. What OpenTelemetry Is

**OpenTelemetry (OTel)** is a vendor-neutral set of APIs, SDKs, and a Collector for producing, moving, and exporting telemetry — so apps are not locked to one backend. Example: the same app can send traces to Jaeger today and another trace backend later by changing the Collector export, not app code.

## 2. The Three Signals

- **Trace**: a record of one end-to-end request as it crosses services. Example: a checkout request traced from API → payment → inventory.
- **Span**: one timed step inside a trace, with a name, start/end, attributes, and parent/child links. Example: a "charge-card" span inside the checkout trace.
- **Metric**: a number measured over time, used for trends, rates, and alerts. Examples: a counter for requests handled; a histogram for request latency; a gauge for in-flight requests.
- **Log**: a timestamped, human/structured event record for one moment in one service. Example: "payment failed for order X," ideally carrying the same trace_id as the trace.

Why all three: metrics tell you something changed, traces tell you where in the flow, logs tell you what happened in detail. The tutorial's working test: one HTTP request → one multi-span trace + a counter increment + a log line with the same trace_id.

## 3. Context Propagation

**Context** is the request-scoped identity (trace, span, baggage) that travels with work so downstream steps join the same trace.

- **traceparent** (W3C Trace Context): a header carrying trace-id, parent span-id, and sampling flags. Example: Client → Service A → Service B keeps the same trace-id, but each hop creates a new span-id and forwards an updated traceparent.
- **Baggage**: small key-value pairs propagated alongside trace context, e.g. `tenant=acme`. It does not automatically become span attributes — code or a Collector processor must copy it deliberately.
- **In-process propagation**: async context must be preserved so child spans attach to the right parent (the tutorial stresses this for Node.js).

## 4. Instrumentation and SDKs

**API vs. SDK**: the API is what app code calls; the SDK is the implementation that creates, batches, and exports telemetry. Providers configure tracing, metrics, and logging.

- **Auto instrumentation**: library/framework hooks that create spans with no per-operation code. Example: automatic spans for HTTP servers/clients and database drivers. Benefit: fast broad coverage. Cost: many spans, noisy names, possible sensitive attributes — needs filtering/suppression.
- **Manual instrumentation**: hand-written spans around business operations. Example: a span named for "checkout" with domain attributes like order type. Benefit: meaningful boundaries, domain attributes, controlled cardinality.

Tutorial's rule: start with auto for coverage, add manual spans on critical paths, and keep semantic conventions consistent so dashboards/alerts stay stable.

Python example in the tutorial: one Resource (`service.name`, `service.version`, `deployment.environment`), a TracerProvider + BatchSpanProcessor + OTLP span exporter, a MeterProvider + PeriodicExportingMetricReader + OTLP metric exporter, a LoggerProvider + BatchLogRecordProcessor + OTLP log exporter; a span "demo.operation" with attributes, a counter "demo_counter," baggage `user_id=u-123`, and logs that print trace_id/span_id.

## 5. The OpenTelemetry Collector

- **Receiver**: listens for telemetry in. Example: OTLP over gRPC on 4317 and HTTP on 4318.
- **Processor**: changes or controls flow between receive and export. Examples: batch (fewer, larger exports); memory_limiter (avoid OOM).
- **Exporter**: sends telemetry onward. Examples: to Jaeger, Prometheus, Loki, or, in the tutorial's minimal config, logging exporters for local visibility.
- **Pipeline**: receiver(s) → processor(s) → exporter(s), defined separately per signal. Example: three pipelines — traces, metrics, logs — each with OTLP receiver + batch processor + its own exporter. Separate pipelines let you tail-sample traces without touching metrics.
- **Extensions**: sidecar capabilities such as health_check (tutorial used 0.0.0.0:13133).
- Common early mistake: exporter protocol/port in the app not matching the Collector receiver endpoint.

## 6. Sampling

- **Head sampling**: decide at span start, usually in the SDK. Example: keep 10% of traces from the start. Benefit: cheap, lowers downstream load. Risk: you can discard a trace before you know it will be interesting (e.g., it later errors).
- **Tail sampling**: decide after the full trace is seen, usually in the Collector. Example: keep all error or high-latency traces, drop healthy ones. Benefit: policy-based retention. Cost: buffering/memory, delay, traces that never complete, bias toward services emitting more spans.

Practical default from the tutorial: modest head sampling in the SDK in steady state; add tail sampling in the Collector only if you can afford buffering and need policy-based retention.

## 7. Backends

- **Trace backend — Jaeger**: stores and shows traces; you search by trace-id/service and inspect span waterfalls. The tutorial's diagram/lab used Jaeger.
- **Trace backend — Tempo**: the Grafana-native alternative to Jaeger in the same trace-backend slot (the tutorial did not detail Tempo separately).
- **Prometheus**: stores metrics (scrape/remote-write) and answers aggregate queries/alerts. Example: error rate or p95 latency by service.
- **Loki**: stores logs, indexed for search. Example: find all logs with a given trace_id.
- **Grafana**: visualizes/queries Prometheus and Loki, and links logs ↔ traces by trace_id.

Ownership split: SDKs create telemetry; Collector routes/transforms it; backends store and query it. Diagnose by layer: missing context = instrumentation/propagation; missing/transformed data = Collector; missing query results = backend/config.

## 8. End-to-End Architecture (Minimal Pipeline)

App (SDK, OTLP exporters) → OTLP → OpenTelemetry Collector (OTLP receiver → batch/memory_limiter processors → per-signal pipelines) → Traces → Jaeger (or Tempo); Metrics → Prometheus; Logs → Loki → Grafana queries Prometheus/Loki and links to traces.

Local lab in the tutorial: Docker Compose with otel-collector, jaeger, prometheus, loki, grafana; app sends OTLP to the Collector; smoke tests are Collector starting without config errors and Prometheus targets up. ## 9. Interview-Ready Talking Points: "Walk Me Through Building Observability from Scratch"

- **Follow one request**: "I'd instrument the app with OTLP exporters, propagate traceparent, send everything to a Collector, batch/enrich there, then export traces to a trace backend, metrics to Prometheus, and logs to Loki, with consistent labels and trace–log correlation."
- **Start with the outcome**: define the proof — one request produces one trace, a counter, and a correlated log.
- **Justify instrumentation**: auto for baseline coverage, manual for business-critical paths; consistent semantic conventions; control cardinality (never put user IDs / unbounded values in metric labels).
- **Justify the Collector**: decouple apps from backends, one place for batching, filtering, enrichment, routing; separate pipelines per signal.
- **Justify sampling**: head sampling for cheap steady-state control, tail sampling only when you need error/latency retention and can pay buffering cost.
- **Name failure modes**: context loss at service boundaries, async-context loss, mismatched OTLP protocol/port, high-cardinality attributes, tail-sampling buffer pressure, unsampled-but-important traces under head sampling.
- **Close with verification**: trace-id search across Jaeger/Grafana/Loki, a metric that moves when you send traffic, and an alert on that metric — not just "data is flowing."
