# 评估体系（Ch4）：Eval Set、打分、诊断、回归

> 核心观点：没有真实 eval set，"it works"的意思是"在我试的三个例子上 work"。评估是整个 lifecycle 的地基。

## 1. 从真实 Case 建 Eval Set

- **Eval set**：一组固定的代表性测试 case + 已知正确的期望答案（**golden responses**，判分依据），用来客观打分。
- **必须从真实 case 来**：生产日志、真实工单。纯 synthetic 的 case 考的是你的想象力，不是用户。
- **打标签**：退款问题/愤怒客户/edge case……让失败能聚类。**50 个 case × 5 个检查字段 = 250 个检查点**——单 case 多检查，胜过堆 case 数量。
- **锁一个 golden 子集永不改**：它是回归基线。
- 顺序：**先收集真实 case，再定稿 prompt**——eval set 是功能的 ground truth。

## 2. 打分：方法阶梯

按成本和判断力排个梯子：
- **Exact match**：确定性字段。
- **逐字段检查**：结构化输出的每个字段。
- **Rubric + LLM judge**：**LLM judge** = 用第二个模型按书面 rubric 打分，处理主观质量。**Rubric 是全部**："提到退款金额和政策例外"判得准；"这是个好摘要吗？"只是把含糊挪了一层。
- **人工抽查**：锚定一切的基准。

看**通过率**（pass rate）整体 + 按标签分，看哪类 case 挂。小例子：摘要按三个二值项打分（分类对/提到关键事实/没编造），不要一个"感觉分"。
**先投 rubric，再信分数**——含糊的判分器给你的是包装成指标的噪声。

## 3. 故障诊断：五个问题

按顺序问，不许跳：
1. **什么挂了**——哪些 case，按标签聚类？
2. **怎么挂的**——字段错/内容错/格式错？
3. **管线的哪一段**——prompt / retrieval / 格式化 / 周边代码？
4. **为什么**——缺信息/指令含糊/误导性样本？
5. **最小的根因修复是什么？**

纪律：**先聚类再修；永远别凭感觉重写 prompt**。例：10 个退款失败都缺同一条政策条款 → 这是 retrieval 的问题，不是措辞问题。
**定位不到管线阶段的故障，还没到修的时候**。

## 4. 把评估接进工作流（防回归）

- **Regression（回归）**：一次改动（prompt 编辑、模型版本升级）把以前过的 case 搞挂了。
- 防御：每次改 prompt/模型都跑 eval set；定时跑（nightly）；当发布门禁。pass rate 掉 vs  locked baseline 就 block 发布。
- 关键运营细节：示例 eval 跑一次约 7 秒——**eval 必须快到能一直跑**，慢的 suite 没人跑。
- 反模式：把 regression"转正"成新 baseline 让数字变绿。
- **把 eval 接进和单元测试一样的自动化**。

## 自测 4 问（带答案要点）
1. Eval set 为什么必须来自真实 case？golden 子集干嘛的？
   → synthetic 考想象力；locked golden 是回归基线。
2. Rubric 为什么是打分的全部？
   → 含糊的判分标准产出噪声指标；先投 rubric 再信分数。
3. 诊断五个问题是什么？核心纪律？
   → 什么/怎么/哪段/为什么/最小修复；先聚类再修，不凭感觉改 prompt。
4. Regression 的三道防线？
   → 每次改动跑、定时跑、发布门禁；pass rate 掉就 block。
