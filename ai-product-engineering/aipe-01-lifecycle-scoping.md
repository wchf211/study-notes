# AI 产品工程：生命周期 + Scoping（Ch1–2）

> 核心观点：调模型 API 是最容易的部分，真正的功夫在 API 周围的产品工程。这门课给了一套闭环方法论。

## 1. AI 产品工程是什么

AI 产品工程 = 让 LLM 功能在生产环境**可靠**的整套功夫。五个职责：
1. **Scope**：这个功能到底需不需要 AI？
2. **Specify**：把 prompt 写成 contract（下游代码依赖它）。
3. **Evaluate**：用真实 case 证明它 work，而不是肉眼看三个例子。
4. **Choose capabilities**：RAG / tool calling / fine-tuning，只在诊断出的故障需要时才加。
5. **Operate**：上线后防御、加固、监控。

关键认知：**模型质量 ≠ 产品质量**——模型 99% 的时候都对，但错的那 1% 正好是最贵的地方，这门课就是系统性地补这个 gap。

## 2. 生命周期（Lifecycle）：是个环，不是直线

**Scope → Specify（prompt 写成 contract）→ Evaluate（跑测试集）→ Diagnose（找根因）→ Fix（最小改动）→ Monitor（盯生产）→ 回到 Evaluate**。

贯穿全课的例子（客服工单摘要器）：baseline prompt 50 题过 40 题；退款政策类全挂；诊断发现模型根本没读过政策文本 → fix 是加 retrieval（把政策文档喂进 prompt），不是重写 prompt。

铁律：**永远不要从"发现故障"直接跳到"修"**，中间必须经过诊断。

## 3. 值不值得做：三个门禁问题

1. **真的需要 AI 吗？** 确定性代码/规则能搞定的别上 AI。AI 适合模糊、多变的输入，不适合有标准答案的事。
2. **错一次的代价多大？** （blast radius）便宜、可逆的错（草稿、建议回复）是 AI 的好地盘；贵、不可逆的（医疗建议、转钱、法律决定）要强得多的理由。例：工单自动分类（错了人工一眼看出）vs 自动批准退款（错了直接亏钱）。
3. **团队养得起吗？** 测试数据、eval 维护、监控、模型成本，都是长期开销。

大多数 AI 功能的失败是 **scoping 失败**——一开始就把错的问题交给了模型。**把"错的代价"写下来**，它驱动后面所有设计决策。

## 4. Failure Boundary + Abstain（主动认怂）

- **Failure boundary（故障边界）**：事先画一条线，线这边模型说了算，线那边停下来转人工。
- **Abstain**：设计好的拒绝——"这个我处理不了"不是丢人，是功能。模式：低置信/高风险走人工；模型**永远**不独自做不可逆操作；按字段划界（摘要器可以起草，但不能直接发送）。
- 例：工单提到"法律行动"，跳过自动分类直送人工队列。
- 先设计"我不知道"的路径，再设计 happy path。没有事先画的边界，故障会出现在最贵的地方——用户面前。

## 5. 为不确定输出设计 UI

模型输出是概率性的（**流利但可能是错的**），UI 要围绕不确定性设计，而不是藏起它：
- 显示校准过的不确定性（"置信度低，请核对"）；
- AI 输出是**可编辑的草稿**，不是自动生效的变更；
- 提供重新生成/备选；高风险步骤留人工；优雅降级（fallback 到非 AI 路径，而不是报错）。
- 例：摘要面板 = 摘要 + 编辑框 + "送审"按钮，而不是静默归档。
- 每个 AI 输出都要回答：**"它错了用户怎么办？"** 把猜测包装成事实的 UI，是在批量制造过度信任。

## 自测 4 问（带答案要点）
1. AI 产品工程的五个职责？
   → Scope / Specify / Evaluate / Choose capabilities / Operate；模型质量 ≠ 产品质量。
2. Lifecycle 为什么是环？铁律是什么？
   → Monitor 回到 Evaluate；永远不要跳过诊断直接修。
3. Scoping 的三个门禁问题？
   → 需不需要 AI / 错的代价 / 养不养得起；把代价写下来。
4. Abstain 为什么是"功能"不是"丢人"？
   → 事先设计的拒绝路径；先设计"我不知道"，再设计 happy path。
