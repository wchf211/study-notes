# AI Systems Architecture (Module 5)

> The course's most reusable technical spine: LLM-based vs. agentic is a runtime distinction, not a model distinction. And the harness — not the model — is where most enterprise production failures originate.

## 1. The AI System Landscape: LLM-Based vs. Agentic

Two categories. The distinction is **runtime operation**, not underlying model capability.

**Non-agentic (LLM-based)**: input → LLM → output, a fixed path, the same input type → the same sequence, no autonomous mid-process actions. Use cases: document classification, extraction, summarization, structured Q&A, content generation (contract clause summary, support routing, knowledge retrieval). Advantages: faster to scope, straightforward evaluation, simpler handoff, traceable wrong output.

**Agentic**: reasons across multiple steps; decides the next action, executes, observes the result, incorporates it, continues until the goal is reached/abandoned. Steps/path are not fixed. Use cases: multi-step research/synthesis, autonomous workflow execution, external API/database interaction to complete a task, conditional document pipelines. FDE work changes: a more thorough evaluation framework, failure-mode analysis, a handoff covering mid-task failure.

What makes a system agentic: perceives the environment, reasons toward a goal, selects/executes actions, observes results, repeats until the goal is reached/abandoned. The defining property is **autonomous multi-step operation determining its own next action** without a human directing each step. Labeling "agentic" for any agent-framework system is widespread but wrong — it depends on autonomous actions across steps based on observations.

Every agentic system has two structural parts: a **reasoning model** + **harness engineering**. The reasoning model is the LLM at the center, perceiving state, deciding the next action, generating output/instruction per step. Reasoning models (deliberate step-by-step inference) are better for planning/decomposition/conditional logic. Model choice is a scoping decision by task complexity — but the model alone does not equal production reliability.

**Harness engineering** is the operational environment around the model: tools, memory, context across steps, guardrails (safe boundaries), observability (a record of what it did and why). The same model with a different harness produces very different production performance. The harness determines safety, failed-action handling, cost limits, post-hoc understandability. Most enterprise production failures originate in the harness, not the model.

Harness components: Tools (functions to interact: APIs, databases, search, code execution, internal enterprise services; how the agent acts beyond text; the FDE defines access in scoping — broader access means capability + failure surface); Memory (within-session + across sessions; short-term is the active context, long-term is an external vector/structured store); Context management (what is included in each call, prioritization as the session grows, compression near the window limit — overflow is a consistent production failure); Guardrails (what it can/cannot do: tools, actions, outputs, cost/token limits per session; design before build, not retrofit); Observability (logging/tracing every action, tool call, decision, cost — without it the team cannot understand/diagnose); AI review loops (evaluation between output and delivery: self-reflection or a critic model; fail → regenerate; exceed retries → human); Orchestration (coordination for multi-agent: sequential/parallel/loops/central coordinator; each agent retains its own harness; orchestration is how they connect, pass state, handle cross-agent failures).

Productive questions for a customer-built agentic system: tools, context across long sessions, tool-failure handling, where the record of actions lives. A system without an observable harness is one the customer cannot safely own.

## 2. LLM-Based Systems: Four Patterns + RAG + Fine-Tuning

Many highest-value workflows need no multi-step reasoning/tool orchestration/autonomous action. A well-scoped LLM system delivers measurable value faster with less operational overhead.

Four patterns:
- **Classification** — input → predefined category (e.g., support ticket routing). Evaluation: precision/recall vs. an agreed labeled test set defined in scoping.
- **Extraction** — structured data from unstructured text (e.g., contract parties/dates/payment terms). Evaluation needs a gold-standard set of correctly extracted outputs from real customer documents, defined pre-build.
- **Summarization / synthesis** — compress/combine into a shorter structured output (e.g., research reports → executive briefs, multi-document aggregation). Evaluation needs coverage, factual accuracy thresholds, format criteria pre-defined.
- **Q&A / generation** — a natural-language answer/content from a prompt (e.g., policy Q&A, draft emails). Factual accuracy + format criteria; a human-review step is a scoping decision pre-build.

Classification/extraction have clean measurable evaluation; summarization/generation need deliberate upfront definition of good output. Evaluation design belongs in scoping, not after build.

**RAG**: a retrieval layer before generation — documents chunked/embedded/indexed in a vector store ahead of time; a query → fetch the most relevant chunks by semantic similarity → assemble context + query → the model generates from retrieved content. RAG fits when: the knowledge base is too large for a single context window; it is frequently updated / needs the latest information; output must trace to sources for legal/compliance/audit; or the customer already has a structured document repository to connect. Evaluate RAG: **retrieval quality first** — a capable model on poor retrieval produces poor answers. Validate the right documents are retrieved for real queries in the POC before blaming the model. Four areas: chunking strategy (poor splitting means relevant information is split across chunks never retrieved together; ask in scoping, validate vs. real queries in the POC); data freshness (update frequency, staleness impact for time-sensitive queries); context window fit (retrieved documents fit for the most complex queries — overflow is a silent failure surfacing only under real production load); ingestion pipeline ownership (who adds new documents, what triggers re-indexing — no owner post-FDE means silent degradation as the knowledge base grows).

**Fine-tuning**: adapts a pre-trained model on labeled domain examples, updates weights, shifts behavior to a specific task. Fits when: the base model consistently underperforms on domain inputs/formats that prompting cannot close; needs a consistent output structure a general model does not sustain across variation; or token cost/latency at projected volume makes a leaner model more practical than long system prompts at scale. Two types: **Full fine-tuning** (all weights; highest adaptation, significant compute/storage/data; most enterprise deployments avoid unless genuinely required); **PEFT** (parameter-efficient; a small subset; much less compute/storage; most enterprise fine-tuning today) — **LoRA** (low-rank adaptation; small trainable matrices inserted into layers, near-full quality at a fraction of the cost), **QLoRA** (quantized LoRA; LoRA on a quantized model, further memory reduction, smaller hardware). The FDE need not run the jobs; understanding the approach informs timeline, data requirements, post-handoff maintenance. Scope fine-tuning only when POC evidence shows the base model cannot close the gap — it adds complexity + customer-owned maintenance: dataset curation, retraining triggers, model version management. The handoff document covers dataset ownership, evaluation cadence, updates when the domain evolves.

When to recommend LLM-based — five signals: meaningful output from a single/small number of model calls, no autonomous mid-process actions; a consistent well-defined input type → straightforward evaluation pre-build; no external services / multi-step coordination needed; the customer team needs a debuggable/maintainable system without reasoning about multi-step execution/tool coordination/session state; latency/cost constraint (LLM systems are faster/cheaper than agentic at the same problem class).

**The most common scoping error is recommending agentic for a problem LLM-based solves reliably.** Start with the simplest architecture addressing the problem and add complexity only when clearly required.

Comparison: LLM-based = single-step output, no tool calls, low/predictable latency, straightforward maintenance. Agentic = multi-step output, tool calls required, variable latency, observability required.

## 3. Harness: Tools, Memory, Context

Agentic = a reasoning model inside an engineered environment. The model decides; the harness determines whether a decision can be executed safely/reliably. The harness is where most enterprise deployment decisions live. Focusing on model selection + the harness as an afterthought means a demo works but real operations fail. Production failures almost always trace to an underdefined/misconfigured/missing harness component.

The reasoning loop has four phases: **Perceive** (current state: what is known so far, tool returns, new input, what remains to accomplish) → **Reason** (the model processes state and determines the next action) → **Act** (execute: tool call, retrieval, output generation) → **Observe** (receive the result, incorporate into an updated picture). Repeat until the goal, a defined stopping condition, or an unresolvable error. Scoping questions: what causes a stop, what happens when a step fails, how many iterations a realistic task requires — these reveal predictable vs. unplanned failure modes.

**Tools**: functions the agent calls to interact with external systems. Without tools it can reason/plan but cannot retrieve live data, update a record, or trigger a workflow. Tool calling per step: the model selects a tool + generates arguments → the harness executes the function and receives a result → the result is passed back as a new input for the next reasoning step. Three categories by risk: **Read tools** (retrieve from databases/knowledge bases/document stores/external APIs; no external state change; lowest risk); **Write tools** (update records, post APIs, send notifications, trigger workflow steps; failures affect external systems and may be irreversible without manual intervention); **Execution tools** (run scripts, invoke compute, initiate longer-running processes; highest risk; failures can produce side effects beyond the session). Multi-tool coordination: the output of one is often the input to the next; independent sub-tasks can run in parallel, and the agent synthesizes before continuing. The FDE defines the minimum tool set in scoping. Broader access means capability + failure surface. Write-to-production risk belongs in the scope document pre-build.

**Memory** — two levels: **Short-term** is the active context window within a single session (goal, prior tool results, observations, running state; directly available each step but bounded by the window). **Long-term** is persistent storage read/written across sessions (typically vector stores for semantic retrieval or structured databases for exact lookups; recall prior interactions, accumulated knowledge, resume multi-session tasks). The boundary is an architectural scoping decision: self-contained single-session tasks need short-term only; cross-session / prior-interaction recall / accumulating findings require long-term. Ask session-continuity requirements in scoping, not the pilot (redesign under time pressure).

**Context management** governs what goes into each model call: goal, prior observations, tool results, retrieved documents, other needed information. The quality of assembly drives the quality of reasoning. The window is fixed; competing content grows as the session progresses. Three approaches: **step summarization** (compress earlier steps into a summary before the window fills, preserve key outcomes without full detail); **selective retrieval** (tool results/documents stored externally, retrieved into context only when relevant to the current step, not every call after first appearance); **running state** (a structured progress summary updated each step, replacing carrying the full history verbatim).

**Context window overflow is a consistent production failure**: when the window fills, content is dropped without the model explicitly signaling. The agent continues from an incomplete picture. Outputs can appear plausible while wrong because needed information is silently absent. Validate context behavior in the pilot using session lengths and input volumes matching real production. A short demo that is OK can degrade silently when sessions lengthen / tool calls accumulate at real volumes.

Components are not independent: a well-scoped tool set reduces context noise; accurate context management means reasoning from complete information; memory architecture determines handling of realistic session lengths/volumes. Evaluate and validate together in scoping/pilot.

## 4. Harness: Guardrails, Observability, Review

Tools/memory/context make a loop functional, not safe/reliable under real conditions. Guardrails, observability, and AI review loops are harness components (constrain, record, evaluate from within). Human escalation is an **operational workflow** designed alongside the system, outside the harness, for cases needing human judgment before action/output. Define it in the same scoping/handoff work. Absent/underdefined means behavior is hard to predict, failures are hard to trace, no reliable intervention path.

**Guardrails**: constraints defining what the agent is permitted to do at runtime; safe operating boundaries before build. The need follows from tools: write access → consequential irreversible actions; user-facing queries → high cost/session. Without explicit constraints the only limit is the model's per-step judgment, which is not reliable safety at production scale. Four types: **Scope limits** (which tools/actions are permitted; prevents an agent tasked with research calling an unintended write tool); **Budget ceilings** (token/cost limits per session/day — a single runaway session can consume a month's API budget); **Output filters** (validate content/format before the user; without, PII/hallucinated content surfaces; enforce format, strip disallowed content, flag outputs exceeding risk thresholds); **Permission controls** (which data can be read/written; enterprise agents often have access to sensitive stores beyond task need; limit to workflow need). Guardrail configuration is a scoping artifact, not a post-build checklist. Define it in the scope document, verify it holds vs. edge-case inputs in the pilot, include it in the handoff with guidance on adjusting as the system evolves.

**Observability / tracing**: a logging/tracing layer recording what the agent did each reasoning-loop step and why. It makes failures diagnosable vs. invisible. An agentic wrong output often originated several steps earlier (an unexpected tool result, incorrect context assembly, reasoning from an incomplete picture). Without a trace the team cannot find the origin. **Execution tracing** is a complete sequential step-by-step session record: per iteration what the model received, decided, tool called, tool returned. It allows exact reconstruction. Log six dimensions: tool calls + results including errors/retries; model inputs/outputs each reasoning step; memory reads/writes including long-term retrieval/write-back; token usage/cost per step/session; error states, timeouts, retry behavior; confidence scores where surfaced at decision points.

Diagnostic test before closing the pilot: if the agent produces a wrong output next week, can the customer team reconstruct exactly what happened? If no, the harness is not ready for handoff. Confirm observability produces readable traces and the team can interpret them before the pilot ends.

**AI review loops**: an evaluation step between output and delivery. Output is checked vs. defined criteria; pass → delivered; fail → regenerate adjusting based on review feedback; still fail after defined retries → human review. Two forms: **Self-reflection** (the agent is prompted to evaluate its own output pre-return; criteria: grounded in retrieved documents, format requirements satisfied, all required steps completed; identifies failures and regenerates); **Critic model** (a separate model instance / dedicated critic prompt evaluates independently; decides accept, send back with specific feedback, or route to a human). Fits when output quality is critical on verifiable dimensions (format compliance, factual grounding, constraint satisfaction) and per-step human review would create unacceptable latency. It adds token cost + latency/output; estimate review-step cost at projected volume before including it in scope. Review criteria must be defined precisely in scoping (vague → unreliable review). Set a retry limit in pilot configuration (how many regenerations before escalation). It reduces human-review volume and does not eliminate human oversight.

**Human escalation**: confidence thresholds define the point at which the agent routes for human review vs. acts autonomously. The threshold is calibrated in the pilot vs. the real-input output distribution. Too high means review burden; too low means it acts when it should not. The escalation path has four components, defined/documented pre-go-live: who receives it (a named role/team, not a general reference); what accompanies it (the original input, the agent reasoning trace for the session, the confidence score/review failure triggering escalation — reviewers cannot decide usefully without context); how the decision is recorded (the reviewer response is logged; patterns over time inform threshold calibration and surface recurring failure modes); what the agent does while waiting (pause/hold the task open, fall back to a default output, or route to the existing manual process; depends on workflow delay tolerance). Define it in the pilot, document it in the handoff, confirm the team can operate it independently before close.

An ownable system means guardrails documented, observability readable traces, escalation tested/understood pre-FDE exit. Missing any means it fails silently and unpredictably after the engagement in a way no one is equipped to diagnose/fix. Guardrails/observability/review/escalation are not add-on features; they make a system ownable vs. fragile.

## 5. Multi-Agent Orchestration Patterns

A single agent handles a wide range. Some problems exceed one agent in a single session: parallel workstreams, different sub-tasks needing genuinely different tools/capabilities, or total context exceeding one agent's window even with compression. Multi-agent means multiple agents coordinate toward a shared goal; each retains its own reasoning model + harness (tools, memory, context, guardrails). The coordination layer adds concerns: context/state movement, failure in one agent affecting the rest, combined observability/debugging. It is not automatically right — propose it only when the use case justifies the coordination cost. The pattern chosen pre-build determines build complexity, cost/task, what the customer team inherits.

Justified when at least one holds: sub-tasks are independently runnable where parallelism meaningfully reduces completion time; different sub-tasks require distinct tool sets / specialized capabilities a single agent cannot carry efficiently; total context exceeds one agent's window even with compression. If none, a single agent + a well-designed harness means lower cost, simpler debugging, easier handoff. Multi-agent adds coordination complexity, multiplies token consumption, makes failures harder to trace. Estimate cost/latency at projected volume pre-recommendation and present the tradeoff honestly in scoping.

Four orchestration patterns:
- **Sequential** — agents one after another in a fixed pipeline; each completes and passes output to the next; each step transforms the previous output (e.g., research extracts → analysis interprets → drafting produces structured output). Most predictable to debug. Failure is localized to one step, and the trace shows the origin.
- **Parallel** — multiple agents simultaneously on independent sub-tasks, each with its own scope; when all complete, outputs are aggregated (e.g., processing multiple documents simultaneously, researching multiple sources, evaluation pipelines across a large batch). Reduces wall-clock, multiplies token consumption proportional to the number of agents. Estimate cost at projected volume. Aggregation must handle partial failures gracefully — one failure should recover, not discard all.
- **Loop** — an agent/set runs repeatedly until an exit condition: output meets defined quality criteria, a maximum iteration count is reached, or a review marks it complete (e.g., iterative refinement generate-evaluate-revise, research search-assess-completeness-search-again, retry patterns where later steps reveal earlier re-execution is needed). The exit condition must be defined precisely pre-build. A loop without a well-specified termination runs indefinitely. The FDE sets a maximum iteration count + a token budget ceiling in scoping and validates both hold under adversarial inputs in the pilot.
- **Hierarchical** — an orchestrator agent plans/coordinates, subagents execute. The orchestrator decides which subagent to invoke, passes relevant context, receives the result, determines the next step. Subagents do not communicate directly. Suits complex workflows with sequential dependencies, planning/execution meaningfully separate, central state management across sub-task results before the next decision. Can extend multi-level orchestrators→orchestrators→workers. The orchestrator is where most multi-agent failures originate. When a subagent returns unexpected/fails, the orchestrator must decide how to continue. Evaluate the orchestrator's handling of subagent errors/retries/partial results in the pilot before production.

**Agent handoff** (a different structure, not simultaneous coordination): one agent transfers control to another, which takes over continuing from where the first left. The first stops at handoff. No central orchestrator manages both simultaneously. It transfers accumulated task context: the original goal, completed so far, relevant memory, constraints the receiving agent needs. The receiver starts from that context, not scratch. Suits workflows with distinct phases needing genuinely different capabilities/tool sets (intake qualifies → technical resolution; research gathers raw → structured analysis). Context validation at handoff is a design requirement, not an implementation detail. Incomplete/malformed context means the receiver cannot perform reliably. The failure manifests in the second agent but originates in the first — hard to trace without a well-instrumented handoff boundary. Define a valid handoff payload in scoping and validate under realistic inputs in the pilot.

Coordination / reliability — four consistent challenges: **State management** (what context is passed between agents and validated before the receiver acts; hierarchical/handoff incomplete/stale context at transfer causes failures the receiver cannot self-diagnose); **Failure isolation** (when one agent fails, whether/how the system recovers without cascading; parallel handles this naturally via independence; sequential/hierarchical need an explicit fallback at each coordination point); **Multi-agent observability** (debugging requires correlated traces across agent boundaries, not just within one agent; each agent produces its own trace; traces must be linkable to the overall session so the team follows failure origin→surface; an extension of single-agent observability at the system level); **Cost / latency** (multiple agents in parallel/loops multiply token consumption + response time at every coordination step; estimate both at projected task volume pre-recommendation and include per-task cost estimates in the scope document). Account for all four in scoping, set expectations pre-build, document handling in the handoff.

The wrong pattern is expensive to correct mid-sprint: a loop for a task consistently terminating in two steps burns tokens every run; a sequential pattern for two independent steps doubles wall-clock unnecessarily. Identify the fitting pattern in discovery by mapping task structure to the pattern's coordination model, not after the pilot reveals a mismatch.

## 6. Choosing an Agentic Framework

Frameworks implement orchestration patterns, tool binding, memory integration, observability hooks, making a production agentic system buildable. Most enterprise teams reach for a framework vs. building coordination from scratch. The FDE encounters two situations: the customer already has a framework, or starting from scratch needing a recommendation. Both need working knowledge of what each provides, where it fits, post-engagement maintenance cost. Selection is a discovery-phase question. A wrong choice surfaces later as a maintenance problem after the FDE has moved on. It is not the most capable in the abstract — match to the problem, orchestration pattern, and the team that will own the system.

What frameworks provide: orchestration primitives (loop management, branching, conditional execution), tool binding conventions, memory integration patterns, tracing/logging hooks. They reduce implementation time and provide community-maintained scaffolding for components the team would otherwise build/own. What they do NOT supply: design decisions — the FDE still determines the fitting orchestration pattern, guardrail configuration at each agent boundary, handoff payload contents, cross-agent observability instrumentation. A framework makes decisions faster to implement and does not substitute for making them. Evaluate by which supports already-made design decisions and produces an ownable system, not the most features.

Landscape:
- **LangChain** — widely adopted, a broad integration layer (many LLMs, vector stores, retrieval pipelines, external APIs). RAG-augmented workflows, tool-calling pipelines, multi-step chains where each step passes output to the next. Strength is ecosystem breadth (likely an existing integration for the customer's specific vector database/API). Limitation: conditional logic/cycles/persistent state across steps needs additional tooling; for significant branching/state → LangGraph is more appropriate.
- **LangGraph** — extends LangChain, graph-based execution: workflows as directed graphs, nodes are agents/processing functions, edges are transitions. Natively supports sequential, conditional branching, cycles, persistent state. Suits loop orchestration, hierarchical with complex state, conditional routing based on intermediate results. Explicit control over execution flow, logic inspectable each step. A steeper learning curve → factor into the onboarding estimate.
- **CrewAI** — a roles concept: agents as specialists with explicit roles/goals/tool sets. Coordinates via built-in task assignment/delegation/collaboration without manually defining a graph. Suits specialist agents collaborating toward a shared output where coordination is role-based, not state-graph-based. A more readable definition, can help non-technical stakeholders understand. Tradeoff is less granular execution-flow control vs. LangGraph.
- **AutoGen** — Microsoft, conversational multi-agent: agents communicate via structured turn-taking (receive a message, process, produce a response that becomes the next agent's input). Supports automated pipelines + workflows where a human joins the conversation at defined points. Suits tasks where iterative reasoning across agents beats single-pass: code generation/review, document drafting/critique, problem-solving where agents challenge each other's outputs. The conversational structure is explicit/auditable and easier to trace.
- **OpenAI Agents SDK** — purpose-built for tool-calling agents using OpenAI models. Harness-first design, built-in tracing, handoff primitives, native structured coordination. Wraps OpenAI tool use/function calling APIs + orchestration scaffolding. The primary consideration is model affinity: designed around the OpenAI model API, tight integration. GPT reasoning models are a well-supported native path. Needing model flexibility / evaluating alternatives is constraining.
- **Google ADK** (Agent Development Kit) — Google's framework for multi-agent; orchestration primitives, tool integration, native Gemini support. Designed within Google Cloud infrastructure, integrates Google APIs/data services. Suits teams already in Google Cloud or committed to Gemini. No Google Cloud presence means model affinity + infrastructure onboarding cost. Evaluate whether existing infrastructure makes ADK a natural fit or an added dependency complicating handoff.
- **Claude Agent SDK** — Anthropic's SDK for tool-calling agents + multi-agent using Claude models. Agent definition, tool binding, handoff primitives, tracing. Designed for Claude Sonnet + Claude Opus. Suits teams using Claude as the primary reasoning model wanting a supported integrated path. Tradeoff is depth of native integration vs. model-selection flexibility (same as the OpenAI SDK).

Recommend from scratch — five criteria in combination: **Design philosophy fit** (LangGraph directed graphs mean explicit state/flow control; CrewAI roles/collaboration tasks mean specialist coordination thinking; AutoGen conversational turn-taking means iterative refinement; match the expression model to how the team naturally reasons); **Model affinity + vendor flexibility** (a committed provider → an aligned framework gives better native integration/support; wanting to evaluate/maintain flexibility → a model-agnostic framework reduces lock-in); **Observability built in** (frameworks differ in native tracing/logging; limited built-in means the FDE instruments manually, adding build time and leaving the team maintaining custom tooling); **Implementation speed** (a framework the team can get productive with quickly matters when the sprint is 2–3 weeks; weigh the learning curve vs. orchestration gains); **Post-handoff ownership** (a framework the team cannot operate confidently post-FDE is worse than a simpler alternative they can own; estimate the onboarding burden explicitly).

Customer already chosen — three situations: **Fits the use case** → work within it productively; learn the team's existing patterns/conventions before proposing changes. Team familiarity reduces ramp and is maintainable without extra support. **Suboptimal but workable** → work within it; note the tradeoff in the handoff document with a clear explanation of the accepted constraint + what the team should monitor. Do not advocate a switch when the technical case does not justify it. **Genuinely blocks the use case** → recommend a switch framed as a delivery risk; present the specific technical constraint, timeline impact, switching cost vs. continuing cost. The decision belongs to the customer.

Framework selection is an early decision with long-term consequences. A well-matched framework means maintainable/extendable/debuggable independently. A mismatch surfaces slowly post-FDE as build complexity, brittle observability, or a team unable to keep up.
