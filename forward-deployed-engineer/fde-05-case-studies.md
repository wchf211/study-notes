# Case Studies (Modules 7–9): RAG, Multi-Agent, Fine-Tuning

> Pedagogy: each case repeats the same three-beat arc — Decomposing the Problem → System Design → FDE Interview Questions. Same system, three passes: break it into subproblems + constraints, build it, defend it under interview pressure. Design decisions are explicitly traced back to decomposition constraints.

## Case 1: Financial Knowledge Assistant (RAG)

**Setup**: a mid-size investment bank, \~4,000 employees, New York / London / Hong Kong. Analysts, compliance officers, senior advisors lose significant time weekly searching an internal corpus. A typical equity research analyst spends 2–3 hours before writing a note locating prior research, comparable filings, internal memos. Compliance officers manually scan policy documents + regulatory guidance. Senior advisors assembling a pitch book spend half a day locating deal precedents + internal models. Documents live in three places: SharePoint (internal research notes, compliance policies, deal memos organized by client); an email archive (Bloomberg Message + Outlook threads back eight years); a shared file server (SEC filing PDFs, earnings transcripts, older pre-SharePoint documents).

Requirements: all documents + all processing stay within the bank's private cloud; no document content/chunk/query is sent to any external service; respect existing SharePoint permissions — if an employee cannot access a document in SharePoint today, they must not receive an answer derived from it via AI; the same principle extends to the email archive + file server. Ask: employees ask plain-language questions and get accurate answers from internal documents.

Clarifying questions by category: User/workflow (primary users across the three groups; do search patterns differ enough to need different retrieval; what does a failed search look like today per group; expected answer format — brief cited summary, full excerpt, ranked source list; peak usage — earnings season analysts, regulatory audit compliance — affecting availability/latency); Document/source (SharePoint Word/PDF/Excel, regular structured updates — does the folder structure reflect access restrictions? Email archive message threads/attachments, continuous updates — are all message types in one archive or separate systems, what is the thread structure? File server PDFs/scanned, rarely updates — what proportion is scanned requiring OCR? Cross-source: total volume combined? Duplication across sources?); Constraint (private deployment — what infrastructure does the private cloud run, GPU capacity for hosting AI models? If no GPU, provisioning process/timeline? What model review process does IT/security run before an open-weight model can deploy? Access control — are SharePoint permissions structured at folder/library/individual document level? Do email + file server have equivalent permission structures or only SharePoint? How frequently do permissions change? Does SharePoint expose an API returning documents a given user is permitted to access?); Success/measurement (acceptable accuracy threshold per user type — compliance regulatory questions have lower tolerance for a wrong answer than analyst background research; how is accuracy measured; the cost of a wrong answer — a compliance missed reference is a material risk; what does successful deployment look like in 3–6 months?).

**Decomposition** — seven subproblems: Document ingestion (three connectors: SharePoint, email archive, file server; SharePoint exposes the Graph API; email + file server have different access methods; each connector schedule matched to source update frequency); Parsing/preprocessing (PDFs, Word, email threads, scanned files each need different parsing; email needs thread reconstruction + attachment extraction; scanned files need OCR before text is available); Embedding/indexing (chunks embedded using an open-weight embedding model self-hosted on the bank's private infrastructure; no data leaves the environment; embeddings + metadata stored in a vector index within the private cloud); Query handling/retrieval (a user natural-language question is embedded with the same model and matched vs. the index for the most semantically relevant chunks); Access control enforcement (each chunk carries the ACL of its source document as metadata, stored at ingestion; at query time the user's group memberships are resolved and injected as a filter into vector search; search runs only within the permitted subset; a background sync keeps ACL metadata current as permissions change); Answer generation (an open-weight LLM, also self-hosted, receives the retrieved/filtered chunks and generates a grounded cited answer); Evaluation (measure whether answers are accurate, faithful to retrieved sources, complete enough per user type).

Constraints shaping architecture: Private deployment + self-hosted models (all models run on bank-controlled infrastructure; open-weight models make both achievable privately: e.g., BGE or E5 for embedding, instruction-tuned open-weight LLMs such as Llama for generation; the private cloud needs GPU to serve; if no capacity, provisioning is a prerequisite affecting the timeline). Document-level access control (ACL metadata + query-time filter + sync job). Heterogeneous sources (no common access pattern/format/update schedule; SharePoint has a well-documented API + structured metadata; email needs thread reconstruction and may involve two separate storage systems for Bloomberg + Outlook; the file server needs a scheduled crawler + likely substantial scanned documents needing OCR; the ingestion layer is the most engineering effort, with each source entirely distinct handling).

Refined problem statement: design a retrieval + generation system ingesting from three heterogeneous sources, embedding/indexing on self-hosted private infrastructure, scoping each search to only documents the requesting user is permitted to access, generating grounded cited answers using a self-hosted open-weight LLM, evaluated vs. accuracy thresholds defined per user type.

**Design**: two distinct pipelines. The **ingestion pipeline** runs on schedule and populates the vector index with chunks, embeddings, ACL metadata. The **query pipeline** runs in real time: embeds the question, filters the index to permitted documents, retrieves the most relevant chunks, generates a cited answer. Every component in both pipelines runs within the bank's private cloud. The pipelines share the embedding model + vector store.

Ingestion: three connectors pull SharePoint, the email archive, the file server on schedule; each also reads the document ACL at ingestion; the ACL is stored as metadata on every chunk derived from that document. SharePoint connector uses OAuth + Microsoft Graph API; pulls files from configured site collections; API response includes file content + permission settings; fetches Word, PDFs, Excel, each packaged with an ACL and queued for parsing. Email archive connector reads message threads + attachments; reconstructs thread order from headers so a conversation becomes one logical document; attachments extracted and linked to the originating thread by document ID; the archive permission model provides an ACL per thread before parsing. File server connector is a scheduled crawler that walks the directory, identifies new/changed files since the last run, queues them; scanned PDFs flagged so the parser runs OCR before text extraction; folder-level permissions serve as the ACL. All three feed a central processing queue.

Parsing/preprocessing: four document types, different logic. Word/Excel: text + structure extracted directly; headings preserved to support semantic chunking. Text-extractable PDFs: a PDF parsing library extracts the text layer; formatting artifacts cleaned. Scanned PDFs: OCR first, then treated as other extracted PDF content. Email threads: message body extracted and cleaned of repeated quoted-reply chains; attachments processed separately and linked back by document ID. Every document parser also produces metadata: source system, document type, last modified date, ACL from the connector. This travels into chunking with the cleaned text.

Chunking strategy: a chunk too large dilutes retrieval precision; too small loses the context needed for a useful answer. The strategy follows each document type's natural structure. Research reports: semantic chunking at paragraph boundaries — each paragraph is a coherent analytical unit. Compliance policies: hierarchical — a section as parent, a paragraph as child — policies use numbered section references; both levels are needed for retrieval. Deal memos: semantic chunking — variable length but structured; paragraph boundaries preserve context. Email threads: one chunk per message — thread reconstruction already isolates individual messages. Earnings transcripts and PDFs: fixed-size with overlap — no natural paragraph structure; overlap preserves context at chunk boundaries. Every chunk carries document text, source metadata, ACL into embedding and is stored as a single record in the vector store.

Embedding model: an open-weight embedding model converts chunk text to a dense vector; runs on a GPU-enabled host within the bank's private cloud; no document content leaves the environment. Three selection criteria: must run on bank-managed infrastructure with no outbound API calls; the context window must accommodate the longest chunk from the chunking strategies; must perform well on financial-domain text. Open-weight models such as BGE-large-en or E5-large satisfy all three. Served as a local API endpoint both pipelines call. The same model for document embedding at ingestion and question embedding at query ensures both representations live in the same vector space, required for meaningful similarity matching.

Vector store: a shared component between pipelines. Holds every chunk record + supports the filtered hybrid search the query pipeline requires. Three capabilities: metadata filtering (an ACL pre-filter scopes search to the requesting user's permitted documents); self-hosted deployment (must run within the bank's private cloud); scale/speed (several million chunks across three sources, low query latency). Self-hosted options such as Qdrant or Weaviate satisfy all three. Both use **HNSW** (Hierarchical Navigable Small World), an indexing algorithm for approximate nearest-neighbor search maintaining fast query performance as the index grows to millions of records. Each record contains four fields: chunk text, embedding vector, source metadata (document ID, type, source system, last modified date), ACL metadata listing permitted groups for that document. The stored ACL makes permission-scoped search possible without hitting source systems at query time.

Query pipeline and retrieval: (1) The question is embedded using the same model as ingestion → a query vector. (2) The system calls the bank identity provider to resolve the requesting user's current group memberships. (3) A metadata filter is constructed from group memberships; it matches chunks where the ACL includes at least one of the user's groups. (4) The vector store runs a **hybrid search** with the ACL filter applied. Dense retrieval: vector similarity, finds semantically related chunks even when exact words differ. Sparse retrieval: **BM25** (Best Match 25), a keyword ranking algorithm scoring chunks by term frequency + document frequency; effective for precise queries such as regulatory citation numbers, exact ticker symbols, deal names benefiting from exact-match scoring rather than semantic proximity. A weighted combination of both scores produces a final ranked list of permitted chunks. The top-K chunks are passed to an optional reranking step, where a **cross-encoder** model re-scores each chunk against the question with higher precision than first-pass retrieval. Hybrid fits this corpus because the three user groups have different query patterns: analysts ask conceptual questions benefiting dense retrieval; compliance often searches specific regulatory references by citation/exact phrase benefiting BM25; combining serves both without separate pipelines per group. A background permission sync job runs separately from ingestion: it re-fetches ACLs from each source on schedule and updates metadata on affected chunks when permissions change, keeping the stored ACL current without a full re-index.

Answer generation: retrieved chunks are passed to a self-hosted open-weight LLM on a GPU-enabled host within the private cloud. Three decisions: Model selection — the context window must be large enough to hold retrieved chunks + the question together; instruction-tuned open-weight models such as Llama 3 are appropriate and deployable entirely on private infrastructure. Prompt design — the system prompt instructs the model to answer only from retrieved context, cite the source document for each claim, state explicitly when the context does not contain enough information to answer. Citation format — each answer includes the document name + source location so the user can verify against the original; especially important for compliance users whose answers may need traceability to a specific policy/regulatory document.

Evaluation: three dimensions per user group. **Faithfulness**: does the answer contain only claims the retrieved chunks support? An LLM-as-judge evaluates each answer against retrieved context without requiring a labeled dataset upfront. **Retrieval relevance**: are the retrieved chunks relevant? A golden question set, built from known document-answer pairs across the three user groups, provides offline ground truth for both dense and sparse retrieval components. **Completeness per user group**: does the answer cover what the user needed, or did retrieval miss relevant content? Requires periodic human review from a sample of each group, because the acceptable threshold differs: a compliance officer needs a complete answer; an analyst doing background research can tolerate a partial one.

Private deployment: every component runs within the bank's private cloud; no component makes outbound calls beyond the bank's private network boundary. Component table: Embedding model server — GPU-enabled host — shared between ingestion + query pipelines. LLM server — a larger GPU-enabled host — VRAM sized to the chosen generation model. Vector store — a CPU host with persistent storage — self-hosted Qdrant or Weaviate with an HNSW index. BM25 index — a CPU host or colocated with the vector store — a sparse keyword index over the same chunk corpus. Ingestion pipeline — a scheduled job runner — credentials for all three source connectors. Permission sync job — a scheduled job runner — read access to each source's permission API.

Each design decision traces back to a decomposition constraint: private deployment determines viable models; access control drives ACL indexing + permission sync; heterogeneous sources drive the ingestion pipeline structure; the mixed query patterns of the three user groups drive hybrid retrieval. A system designed this way is easier to explain to the customer, easier to hand off, easier to extend when requirements change.

**Interview questions (RAG)** — 15 questions across five sections (one question, Evaluation Q3, was never displayed due to a carousel glitch — see README limitation). Highlights, paraphrased:
- Retrieval: When choose hybrid over semantic alone, and how does the combination work? Hybrid = dense vector retrieval + sparse keyword retrieval. Dense embeds the query, returns chunks by cosine similarity vs. the vector index. Sparse, typically BM25, scores by term frequency + document frequency, favoring exact keyword matches. Two ranked lists are merged via score fusion. **Reciprocal Rank Fusion (RRF)** is common: it sums the reciprocal of each chunk's position across both ranked lists, robust to score scale differences. Dense fits queries where question + document use different vocabulary. BM25 fits lookups where specific exact terms must appear. Hybrid is chosen when the query distribution spans both patterns.
- Retrieval: Why is a cross-encoder used as a reranker rather than a bi-encoder? A bi-encoder embeds the query + each document independently; document embeddings are pre-computed. A cross-encoder takes the query + a candidate chunk as a pair, scores them jointly, attends to the interaction between them — more precise but more expensive, so only applied to top candidates after first-pass retrieval.
- Retrieval: The system retrieves 20 candidate chunks but the LLM context window fits only 5 — how handle? Standard approach is reranking: a cross-encoder re-scores all 20 candidates, processing each one vs. the query, then pass the top 5. An alternative is reducing chunk size so more chunks fit the same window, but smaller chunks lose context. Reranking is more targeted because it improves which chunks are selected without changing chunking.
- Retrieval: How does parent-child chunking improve retrieval over flat chunking? It stores each document at two levels. A child chunk, typically a paragraph, is the retrieval unit; small child chunks produce precise retrieval because they contain fewer unrelated terms. A large parent (e.g., a section) is the context unit passed to the LLM, preserving surrounding context. It decouples the retrieval unit from the context unit.
- Retrieval: How does **HyDE** (Hypothetical Document Embeddings) work, and what is the primary tradeoff in production? It generates a hypothetical answer to the query using an LLM before retrieval, then embeds the hypothetical answer as the query vector. The hypothetical answer uses the vocabulary + structure of real documents in the corpus, closing the vocabulary gap between user phrasing and document language. Most valuable when a significant vocabulary gap exists. Tradeoff: an extra LLM call adds latency + cost per query.
- Evaluation: How detect whether a bad answer came from poor retrieval or poor generation? Inspect the retrieved chunks directly. If the chunks do not contain the information needed to answer, the failure is retrieval. If the chunks contain correct information and the answer is still wrong, the failure is generation. In practice, log retrieved chunks alongside answers + build an evaluation set of known question-answer pairs with known source documents. For each failing answer, check whether the ground-truth source document appeared in the retrieved set. If absent, tune retrieval parameters. If present and the answer is still incorrect, address generation prompt/model behavior.
- Evaluation: The system achieves high context precision but low faithfulness — diagnose and fix? High context precision means retrieved chunks are relevant to the question. Low faithfulness means the answer contains claims not supported by retrieved context; the model is drawing on pretraining / unsupported inference. The fix is in the system prompt: instruct the model to answer only from retrieved context and to say when the context is insufficient. Adding an LLM-as-judge faithfulness check surfaces which answer types fail most frequently and whether the fix worked.
- Production: How implement per-user access control in enterprise RAG without querying source permissions on every request? Move permission checking from query time to index time. At ingestion, the document ACL is stored as metadata on every chunk. At query time, the user's identity is resolved to current group memberships via the identity provider; a metadata filter is constructed from memberships; vector search runs with the filter applied, so only permitted chunks are candidates. A background sync job re-fetches ACLs from each source on schedule and updates chunk metadata when permissions change. The retrieval step is never slower due to permission enforcement, and no source system is queried during a user request.
- Production: Enterprise RAG returns contradictory answers derived from two different documents on the same topic — handle? First response is transparency: the system surfaces both sources + their claims rather than silently picking one; citations include version/date/modified information. Beyond that, the ingestion pipeline can track document lineage and flag superseded versions of the same document. For documents where contradiction reflects genuine analytical disagreement, the system prompt instructs the model to note the disagreement and present both positions, not synthesize a false consensus.
- Production: Is RAG still the right architecture when an LLM supports a 1M-token context window? For most enterprise knowledge bases, yes. A 1M-token window can hold substantial text, but a corpus of millions of chunks still exceeds it; sending the full corpus per query would be prohibitive in latency/cost. RAG also resolves access control requirements that long context alone cannot address: a system that loads everything cannot scope to permitted documents. Long-context windows are most valuable in combination with RAG, where they allow more retrieved chunks and reduce reranking pressure.
- Adapting: Hong Kong analysts want to query in Mandarin; documents remain in English — what changes? The current embedding model maps only English text to vector space. A multilingual embedding model such as multilingual-E5 maps queries + documents from different languages into the same shared vector space, enabling cross-lingual retrieval: a Mandarin query can retrieve English chunks without a translation step. Switching requires a full re-index because the new model produces a different vector representation for every chunk. The BM25 sparse index also requires adjustment: BM25 is language-specific; a Mandarin query will not match English terms, so for Mandarin queries the hybrid retrieval weight should shift toward the dense component. Generation side: the system prompt instructs the model to respond in the same language as the query, which a multilingual instruction-tuned model handles without further changes. The permission model, connectors, chunking are unchanged.
- Adapting: The compliance team requires: if the system is not confident in an answer, it must decline to respond / route to a human — implement? Add a confidence gate between generation and delivery. Two signals inform the gate. First is retrieval confidence: if the highest-scoring chunk falls below a defined threshold, flag before generation, saving LLM cost. Second is a faithfulness self-check after generation. If either signal indicates low confidence, the system returns a fallback response and logs the original query, retrieved chunks, reason for decline to a human expert queue. Thresholds are calibrated per user group (compliance more conservative). Routed queries become labeled evaluation examples.
- Role: How scope a two-week POC for this system, and what would you cut? A two-week POC proves the hardest technical unknowns, not the full system. For the knowledge assistant, scope to one document source, SharePoint, with a representative subset of document libraries; a working end-to-end flow covering ingestion, chunking, embedding, permission filtering, retrieval, generation; cut the other connectors, the full corpus, full permission sync, production monitoring, etc.
- Role: What are the highest handoff risks for this system, and how surface them before the engagement ends? Three risks stand out. (1) Permission sync job: if it fails silently, ACL metadata becomes stale and users may receive answers derived from documents they should not access; the customer team needs a monitoring signal on this job + a remediation runbook. (2) Embedding model drift: if the bank infrastructure team updates the embedding model without re-indexing existing chunks, query embeddings + chunk embeddings will no longer occupy the same vector space and retrieval quality will degrade without an obvious error. (3) Silent ingestion gaps: if a new SharePoint site is added or a file server directory is reorganized, connectors may miss new content without surfacing an error. Each risk should appear in handoff documentation with a specific monitoring signal + remediation step, not as a general warning but as a named failure mode.

Closing line of the lesson: technical interview questions reward answers grounded in a specific system. Naming the exact component that changes, the metric surfacing a failure, or the risk appearing after handoff carries more weight than describing the same concept in general terms.

## Case 2: Shipment Rerouting Agent (Multi-Agent)

**Setup**: a global freight/logistics company, operations across North America, Europe, Southeast Asia; manages \~45,000 active shipments at any time, routed through a network of 200+ carriers and 30 regional hubs. Problem: when a weather event, port closure, or carrier capacity failure occurs, a disruption coordinator manually checks signals from three separate sources, identifies affected shipments, evaluates alternative routes + carrier slots, executes rerouting by updating records in **SAP TM** (SAP = Systems, Applications, and Products in Data Processing; TM = Transportation Management). The process is labor-intensive, pulling/reconciling data across systems not designed to work together. During peak disruption periods (hurricane season, major port strikes), multiple simultaneous disruptions arrive faster than the team can process one at a time.

Systems: shipment records live in SAP TM, the system of record for all active loads, exposing a REST API for read/write used by other internal tools. Disruption signals come from three sources the operations team monitors today. (1) **Tomorrow.io FleetIQ**, a weather intelligence platform, with route-level weather risk scores + severe-event alerts via a REST API. (2) **Portcast Port Congestion API**, a port congestion intelligence service, with real-time berth wait times, vessel queue data, terminal-level congestion scores for ports the company operates through. (3) **project44**, a multi-modal supply chain visibility platform used to connect with carriers; it aggregates carrier exception signals from **EDI** (Electronic Data Interchange) feeds, carrier APIs, telematics into normalized disruption events; it exposes carrier slot availability + rate quotes via its own API. All three data sources are already integrated into the company's AWS-hosted private cloud environment through scheduled polling jobs run by the operations team.

Requirements: any write action to SAP TM requires explicit human approval before execution; IT security + audit policy prohibits fully automated writes to production systems without a human-in-the-loop step. Carrier selection must respect contractual constraints. Hazardous goods, temperature-controlled freight, oversized loads each have a separate approved-carrier list stored in a relational database the operations team manages. The system must produce a recommendation package in plain language that a non-technical operations coordinator can read and approve without consulting a data analyst.

Ask: When a disruption is detected across any of the three sources, the system should identify all affected shipments in SAP TM, generate ranked rerouting options for each using carrier slot data from project44, calculate the cost of rerouting vs. the cost of delay, deliver a ready-to-act recommendation package to the operations coordinator. The coordinator's role shifts from manually gathering/reconciling data across systems to reviewing a structured recommendation + approving action. After approval, the system executes the SAP TM update + sends carrier notifications through project44.

Clarifying questions — four categories: Workflow/process (who triggers rerouting analysis and what the trigger looks like — does the coordinator monitor three sources on separate dashboards, or does one source typically surface an alert first and others confirm? What level of disruption actually warrants rerouting analysis — not every weather alert / port congestion signal justifies the cost/complexity; the operations team likely has an informal threshold today that needs to become an explicit parameter. Which disruption type triggers analysis most often — weather on road routes, port congestion on ocean lanes, carrier capacity failures each require different data + response logic. Who has authority to approve — the coordinator alone, or manager sign-off above a certain cost threshold? What the coordinator weighs before selecting an alternative — carrier slot availability, rate, delivery time impact, shipment type constraints — each a separate lookup today). Answers map the current decision process step by step and reveal which steps carry judgment to preserve vs. mechanical lookups to automate. Data/systems (FleetIQ — route-level weather risk scores or only location-level alerts? What score/severity constitutes a disruption worth acting on vs. normal weather variability monitored but not responded to? Portcast — what congestion level at a contracted port warrants analysis? Does the API return a congestion score, a predicted wait time, or a binary alert flag? project44 — does the integration return carrier slot availability in real time, or does a rate-quote request take several minutes to resolve? Which carrier exception types currently trigger manual review? SAP TM — what fields identify a shipment's route, carrier, transit ports? Is there a direct field linking each load to its port of transit, or does affected shipment identification require querying across multiple route legs? Approved-carrier database — how is the list structured and accessed? How frequently does it change when carrier certifications/contracts are updated? Cross-source: When a Tomorrow.io severe weather score + a project44 carrier exception point to the same port on the same day, do they represent one disruption or two separate events? How the system deduplicates signals matters for how many rerouting analyses it triggers). Answers determine what each agent can call as a tool + what data is available when a disruption event fires. Risk/authority (What does a wrong rerouting decision cost in practice? A penalty from a carrier contract, a missed **SLA** (Service Level Agreement), or a shipment diverted to a longer route each carries a different financial/reputational consequence. Which failure mode is more costly: triggering an unnecessary reroute from a low-confidence signal, or missing a real disruption because the threshold is set too high? Has the company ever had an automated system write to SAP TM before? If this is the first time production shipment records would be updated by a non-human process, the approval workflow needs to be conservative + fully auditable from day one. Above what cost threshold does a decision escalate beyond the coordinator to a manager? The answer sets the boundary between coordinator-level approval + escalation and shapes how the recommendation package is structured). Answers define the approval model and determine how conservative the disruption threshold + confidence checks need to be before a recommendation is delivered. Success/scope (Which disruption type causes the most operational impact per quarter? Building for the most costly type first makes the initial delivery easier to justify + gives a clear comparison vs. the manual process. Which shipment categories are the highest priority? Hazardous goods, temperature-controlled freight, high-volume standard loads each have different carrier constraint complexity + different SLA pressure. What does a useful recommendation package look like when several disruptions arrive simultaneously? A coordinator managing multiple events needs a view allowing triage + quick action, not a detailed report per shipment requiring full reading before any decision. What does success look like after the first three months? Whether measured by a reduction in manual steps, fewer missed rerouting windows, or coordinator time freed up shapes what the system tracks + what the first evaluation report covers). Answers set the scope of the initial delivery + clarify what the operations team will use to judge whether the system is working.

**Decomposition** — six discrete subproblems (each with different data inputs, reasoning, tolerance for error — the combination makes this a multi-agent problem rather than a single agent handling everything in sequence): (1) Disruption detection: monitor Tomorrow.io FleetIQ, Portcast, project44 on schedule; normalize signals from three different schemas into a consistent disruption event format; apply a disruption threshold before triggering downstream analysis. (2) Affected shipment identification: query SAP TM for active shipments on the affected route, port, or carrier; map each confirmed disruption event to specific load records; output a structured list of affected shipment IDs with disruption type, severity, estimated delay impact per shipment. (3) Route + carrier option generation: for each affected shipment, query project44 for alternative carrier slots; filter every candidate against the approved carrier list for that shipment type before scoring; rank alternatives by delivery time impact, carrier availability, fit against the shipment's contractual constraints. (4) Cost + feasibility calculation: calculate the cost of each candidate alternative route vs. the estimated cost of leaving the shipment on its delayed path; flag cases where neither option is clearly better and mark for escalation with both scenarios presented side by side. (5) Recommendation packaging: assemble a structured, plain-language package covering affected shipments, recommended routes, cost comparison, reasoning behind each recommendation; the coordinator must be able to read and act without querying raw data from any underlying system. (6) Execution + notification: after the coordinator approves, write the rerouting decision to SAP TM via the REST API + send carrier notifications through project44; log every action with a timestamp + the identity of the approving coordinator for the audit record.

Constraints shaping architecture — three: **Human approval gates every SAP TM write**: IT security + audit policy is non-negotiable; the execution step cannot write to SAP TM without a structured approval signal from the coordinator; the system holds the recommendation open after delivery and does not proceed until approval arrives; the audit log must record the coordinator identity + timestamp of each approval, not just the outcome of the write. **Approved-carrier lists constrain option generation before scoring**: the route/carrier option step cannot propose a carrier not on the approved list for that shipment type; filtering must happen before ranking; a recommendation including a non-approved carrier would fail compliance review + undermine coordinator trust from first use. **Concurrent disruption events require parallel execution**: when multiple disruptions arrive simultaneously from different sources, the system must handle each as an independent analysis chain running in parallel; the orchestration layer must isolate chains so data from one disruption does not affect analysis for another, and a slow/failed chain for one event does not block recommendations for others.

Refined problem statement: design a multi-agent system that monitors Tomorrow.io FleetIQ, the Portcast Port Congestion API, project44 for disruption signals above an agreed threshold; identifies affected SAP TM shipment records; generates rerouting options constrained by approved-carrier lists per shipment type; calculates a cost comparison vs. delay cost; delivers a coordinator-readable recommendation package; executes the approved SAP TM update + project44 carrier notification with a full audit log. Structured decomposition makes the design defensible by providing a clear rationale for each design decision; the six subproblems identify the engineering work; the three constraints determine available design choices; the approval boundary establishes the liability model the company's audit team will require before the system touches SAP TM.

**Design**: two layers — a set of specialized agents, each responsible for one subproblem, + an orchestration layer that coordinates how those agents are triggered, sequenced, run in parallel. Data sources (five): Tomorrow.io FleetIQ — route-level weather risk scores and severe-event alerts — REST API, scheduled polling; Portcast Port Congestion API — berth wait times, vessel queue depth, terminal-level congestion scores for contracted ports — REST API, scheduled polling; project44 — carrier exception signals from EDI feeds, also exposes carrier slot availability and rate quotes — REST API, polled and on-demand; SAP TM REST API — system of record for all active shipments; supports read for shipment lookup and write for rerouting execution — REST API; write operations require a human approval signal; Approved-carrier database — approved carrier lists per shipment type, maintained by the operations team — relational database, read-only. The SAP TM write is the only interaction that requires a gating step before the system can call it; every other source is read-only from the agent layer's perspective.

Agent design: five agents carry the core logic. The first four run automatically. The fifth holds for a human approval signal before it can write to SAP TM.

- **Disruption detection agent**: fetches signals from Tomorrow.io FleetIQ, the Portcast Port Congestion API, the project44 carrier exception feed on a schedule; normalizes outputs from three different schemas into a shared disruption event format, then removes duplicate signals that reference the same port, route, or carrier from different sources; after removing duplicates, applies the disruption threshold agreed on during the engagement; signals below the threshold are logged but do not trigger a downstream chain. Input: scheduled trigger. Tools (five): three connect to external disruption sources; two are internal function tools that process the collected signals. Tomorrow.io FleetIQ API (fetches route-level weather risk scores and severe-event alerts; returns a severity score the agent applies against the disruption threshold); Portcast Port Congestion API (fetches berth wait times, vessel queue depth, terminal-level congestion scores at contracted ports); project44 Carrier Exception Feed (retrieves normalized carrier exception events aggregated from EDI feeds, carrier APIs, telematics; the source of carrier-side disruptions such as capacity failures and service interruptions, separate from port congestion); Normalization function (converts raw outputs from all three sources into a single shared disruption event format so signals can be compared and processed consistently); Remove duplicates function (identifies and removes duplicate events where signals from different sources point to the same disruption before the threshold check runs). Output: a confirmed disruption event record containing source, affected port, route or carrier, severity score, event timestamp.
- **Affected shipment identification agent**: receives a confirmed disruption event and queries SAP TM for all active shipments routed through the affected port, route, or carrier; the query checks transit ports across all route legs; many disruptions affect intermediate ports rather than a shipment's origin or final destination, so a query limited to those two fields would miss affected loads. Input: confirmed disruption event record. Tool: SAP TM Read API (queries active shipment records by affected port, route, or carrier; checks transit ports across all route legs to ensure mid-route shipments are not missed). Output: a list of affected shipment IDs with disruption type, severity, estimated delay per shipment.
- **Route and carrier option generation agent**: uses a router pattern; the parent receives the affected shipment list and spawns one sub-agent instance per shipment; all instances run in parallel; when all have returned results, the parent assembles them into a ranked output by shipment. Parent agent: Input: affected shipment list; Output: ranked alternatives per shipment, collected from all sub-agent instances. Sub-agent (one instance per shipment): Input: a single shipment ID and disruption event context; Tools (two): project44 Carrier API (queries carrier slot availability and rate quotes for the affected route of the assigned shipment); Approved-carrier database (returns the approved carrier list for the shipment type; used to filter candidates before any ranking runs; non-approved carriers are removed from the set before scoring). Output: ranked alternatives for the assigned shipment, filtered to approved carriers only.
- **Recommendation agent**: receives the ranked alternatives per shipment and the affected shipment list with estimated delay per shipment; calculates the cost of each rerouting option against the estimated cost of leaving the shipment on its delayed path; where neither option produces a clearly better outcome, flags that shipment for escalation; after calculating costs, assembles the full coordinator-readable recommendation package; escalated shipments appear at the top; each entry covers the affected shipment, the recommended rerouting option, the cost comparison, the reasoning behind it in plain language that a non-technical operations coordinator can act on without querying any underlying system directly. Input: ranked alternatives per shipment (from the option generation agent) and the affected shipment list with estimated delay per shipment (from the identification agent). Tool: Internal contract rate table (returns contracted rates and SLA cost parameters for the affected shipment; used to calculate the difference between each rerouting option and leaving the shipment on its delayed path). Output: a plain-language recommendation package covering affected shipments, ranked rerouting options, cost comparisons, a decision signal per shipment, with escalated items surfaced at the top.
- **Execution agent**: holds the recommendation open after delivery and does not proceed until a structured approval signal arrives from the coordinator; the signal contains the coordinator's identity, a timestamp, a decision value; after approval is received, the agent writes the rerouting record to SAP TM and sends carrier notifications through project44; every SAP TM write is logged alongside the approval identity and timestamp; that log is the audit record the company's IT security and compliance policy requires. The agent accepts three decision values: **Approve** triggers the SAP TM write and the carrier notifications; **Escalate** routes the package to a manager queue; **Defer** holds the package open in the coordinator queue without closing the event. Input: an approved recommendation package and coordinator approval signal. Tools (two): SAP TM Write API (writes the rerouting decision to the active shipment record in SAP TM; only called after the coordinator's approval signal is received; the approval identity and timestamp are logged alongside every write); project44 Notification API (sends carrier notifications for the rerouted shipment through the company's existing project44 integration). Output: SAP TM update confirmation, carrier notification status per carrier, a complete audit record for the disruption event.

Orchestration: the orchestration layer coordinates four execution patterns across the agent chain. **Sequential**: the five agents run in order; each agent starts only after the preceding one returns a structured result. **Parallel**: parallelism appears in two places — within the option generation agent, one sub-agent instance per affected shipment runs concurrently; at the orchestration layer, when multiple disruptions arrive simultaneously, each confirmed event spawns an independent chain; those chains share no state; a slow or failed chain for one event does not delay recommendations for another. **Scheduled loop**: the disruption detection agent runs on a continuous schedule; each cycle evaluates all three disruption sources freshly; this is a recurring execution pattern, not a retry loop. **MCP and A2A integration**: two protocols connect the layers. **Model Context Protocol (MCP)**: a standard for connecting agents to external tools through defined interfaces; each external integration is wrapped as a named MCP tool with a fixed input and output schema; every tool call is logged through the MCP layer with a request identifier, input parameters, the response received; that log is what makes the system auditable at the tool level, not only at the level of agent outputs. **Agent-to-Agent protocol (A2A)**: a communication standard for delegation and result collection between agents; the orchestration layer uses A2A to dispatch confirmed disruption events to the agent chain and to spawn independent chains for concurrent events; the option generation router uses A2A to spawn its per-shipment sub-agents and collect their outputs when all instances complete. MCP handles what each agent can call; A2A handles how agents delegate work and return results; the two protocols operate at separate layers and do not overlap.

Evaluation: three dimensions measure whether the deployed system is working correctly. **Disruption precision and recall**: measures whether the detection agent catches real disruption events above the agreed threshold and suppresses noise below it; measured against a labeled set of historical disruption events from all three sources, scored against the decisions the operations team made at the time. **Recommendation accuracy**: measures whether the rerouting options the system generates match what an experienced coordinator would have selected; early in deployment, coordinators flag recommendations they would not have followed, and those cases expand the evaluation set over time. **Audit completeness**: checks that every SAP TM write has a corresponding approval record containing coordinator identity and timestamp; any write without a complete record is a system failure.

Deployment: all components run within the company's AWS-hosted private cloud environment, where the existing polling jobs and data source integrations are already established. Component table: Three polling jobs — scheduled job runner — one per disruption source; credentials stored in the environment's secret manager. Orchestration layer — always-on service — receives confirmed events and manages agent chain dispatch and concurrent event isolation. Five agents — container-based compute — the option generation agent scales sub-agent instances dynamically based on the affected shipment count. Coordinator interface and approval queue — a persistent queue with a web interface — open events persist across coordinator sessions until a decision is recorded. Audit log store — an append-only database — the retention period is set by the company's compliance team. Every design decision traces back to a constraint the case study surfaced; that grounding is what makes the system defensible to present to the customer, practical to hand off to their engineering team, straightforward to extend as the scope grows beyond the initial disruption types.

**Interview questions (Multi-Agent)** — 25 questions across six sections; only the first answer in each section was expanded and read (see README limitation). Paraphrased first answers:
- Orchestration: When design a system as a single agent with many tools rather than multiple specialized agents? A single agent with many tools is appropriate when the task is sequential, when a unified reasoning context produces better decisions than isolated agents, and when coordination overhead would cost more than it saves. Multiple specialized agents make sense when subtasks are genuinely parallelizable, when different subtasks require different models or tool sets, or when isolating one agent's failure from the rest is a hard requirement. The decision comes down to whether parallel execution gains outweigh coordination complexity costs.
- Tool design: How decide which operations to expose as tools vs. handle directly in the agent's prompt? An operation becomes a tool when it requires external data the LLM cannot access directly, when it is deterministic and should not be subject to the model's variability, or when it needs to be logged, retried, or audited independently. Operations that are pure reasoning over information already in context stay in the prompt. Mixing these categories creates tools that do reasoning and prompts that make external calls, both of which are harder to test and debug than their proper counterparts.
- Human-in-the-loop: When should an agent pause and ask for clarification vs. proceed with its best interpretation? An agent should pause when the cost of a wrong interpretation is high relative to the cost of the delay. For reversible, low-stakes actions, proceeding with the best interpretation and logging the assumption is usually appropriate. For irreversible actions, high-cost decisions, or actions that affect systems the agent does not own, pausing for confirmation is the safer default. The threshold should be explicit in the system design rather than left to the model's judgment.
- Reliability and evaluation: How test an agent before deploying it when the task space is too large to enumerate test cases for? Define a representative test suite across task categories rather than task instances. Each category exercises a distinct code path. Use a typical case, an edge case, a failure case, an ambiguous case. Run each test against recorded tool responses so the test is deterministic. For reasoning steps, use an LLM-as-judge to score whether the reasoning matches a reference decision path. This approach scales to large task spaces because it tests behavior patterns rather than individual inputs.
- Production deployment: What log at each step of an agent loop to make failures reproducible? At each step log the agent's input, the tool call issued including name and parameters, the tool's raw response, any state update the agent made after receiving the response, the next action selected. Also log the model version, the prompt version, a timestamp per step. This is enough to replay any run deterministically and isolate the step where behavior diverged from expected.
- Role-specific: How explain the human approval gate to an operations team with no AI background that is worried about losing control over decisions? Frame the approval gate as the coordinator's role being upgraded rather than replaced. Before the system, the coordinator gathered data across multiple sources manually before making a decision. After the system, the coordinator receives a fully assembled recommendation and decides whether to act on it. The decision authority stays with the coordinator. The system handles data gathering and analysis; the coordinator handles judgment and accountability. If that framing does not resolve the concern, ask the team to describe what control means to them and build the interface around that answer.

Closing line: technical interview questions on agentic systems reward answers grounded in specific architecture decisions. Naming the component that enforces a constraint, the log field that surfaces a failure, or the mechanism that gates an irreversible action carries more weight than describing the same concept in general terms.

## Case 3: Hospital Billing System (Fine-Tuning)

**Setup**: a large regional hospital in the Midwest with multiple outpatient clinics; a team of medical coders assigns billing codes across all facilities. Problem: after each patient visit, a physician writes a clinical note describing what the patient presented with, what was assessed, what was done; medical coders read those notes and assign two types of billing codes: **ICD-10** codes (International Classification of Diseases, 10th revision) identify the patient's diagnosis; **CPT** codes (Current Procedural Terminology) identify the procedures and services the physician performed. Insurance companies use these codes to determine how much to reimburse the hospital; if the codes are wrong, the insurer denies the claim; the coder must then review the original note, identify the error, correct the codes, resubmit. The hospital's **first-pass acceptance rate**, the percentage of claims the insurer accepts on the first submission without denial, currently sits at 81%; the industry benchmark is 95%.

Systems: physicians write clinical notes inside **Epic**, the hospital's Electronic Health Record (**EHR**) system; coders access physician notes through Epic and enter their code assignments in the same platform; finalized codes flow from Epic into the billing system, which submits claims to insurers; all systems run on the hospital's private on-premises servers.

Requirements: two constraints apply to any solution: patient records and clinical notes cannot leave the hospital's private environment; **HIPAA** (the Health Insurance Portability and Accountability Act) prohibits sending patient information to external services without authorization the hospital does not hold for this use case. A certified medical coder must review and confirm every AI-generated code assignment before it reaches the insurer; the coder's role shifts from reading the full note and assigning codes from scratch to reviewing the AI suggestion and confirming or correcting it.

Ask: the hospital ran an internal test using an open-weight model on 200 completed encounters from the past year; the model reached 61% first-pass accuracy without any adaptation; the coding director believes the gap exists for two reasons: the hospital's physicians write notes in styles shaped by their individual training backgrounds and local documentation conventions, which differ from the patterns the base model learned during pretraining; the hospital also applies **modifier codes** (additional codes that add detail to a primary code, such as whether a procedure was performed on both sides of the body or on a new vs. established patient) following internal billing guidelines rather than standard defaults. The coding director wants to close the gap to the 95% target and wants to understand what a solution would look like inside their existing environment and whether it is feasible to build and operate.

Clarifying questions — four categories: Task and output (What does the AI output look like for one patient encounter? Does it return a single suggested code set or a ranked list of options the coder chooses from? How many codes does a typical encounter require? Is it usually one diagnosis code and one procedure code, or do most encounters involve several codes across both types? When a coder corrects an AI suggestion, does the system log that correction, or does only the final approved code set get recorded? Does the 95% first-pass target apply to each code in a claim, or to the full claim where every code must be correct for it to count? The answers shape the output format the model must produce and what the evaluation framework treats as correct); Data (How many completed encounters with confirmed correct codes are available from past years to use as training examples? Do physicians across different departments write notes in similar styles, or does note style vary significantly by specialty? Are clinical notes typed directly into Epic, or are they dictated and then automatically transcribed? Transcribed notes often contain different sentence structure and formatting than typed notes. Have the hospital's billing guidelines or modifier code rules changed significantly over the past two years? Training on historical data that reflects outdated guidelines could teach the model patterns that no longer apply. The answers determine whether enough consistent labeled data exists and how much the data preparation step will require before training can begin); Accuracy and evaluation (Which departments or note types produced the most errors in the 61% baseline test? Are the most common errors in diagnosis codes, procedure codes, or modifier codes? Is the 95% target the same across all departments, or are some specialties considered higher priority for accuracy? What happens downstream when a claim is denied? Who reworks it, and how long does the correction process take? The answers reveal whether the gap comes from the model's general capability, its unfamiliarity with the hospital's documentation style, or the complexity of the modifier code rules; each cause points toward a different solution); Deployment and constraint (What computing hardware does the hospital currently have on-premises that could run an AI model? Where in the coder's Epic workflow would the AI suggestion appear? Does the coder see it before or after they begin their own review? How often do billing guidelines and modifier code rules change, and does the model need to be updated each time? What does the hospital's IT team require before an AI system can connect to and read patient notes from Epic?).

**Decomposition** — six discrete subproblems: Labeled data preparation (identifying completed encounters with confirmed correct codes, establishing annotation guidelines that produce consistent labeling across coders, measuring agreement between labelers before any training begins; annotation quality is a prerequisite because inconsistently labeled data teaches the model inconsistent behavior); Approach decision (determining whether the accuracy gap is best closed through a trained model, improved prompting, or another method; this decision depends on what the 61% baseline reveals about where errors come from); Model selection (choosing an open-weight model that runs within the hospital's on-premises hardware, handles the length and structure of physician notes, provides a strong instruction-following foundation to adapt from); Model adaptation (training the selected model on the hospital's coded encounter history using a method that fits within available hardware and reduces the risk of the model overfitting on a limited training set); Evaluation methodology (defining what counts as a correct output at the code level and the claim level, building a test set of encounters the model never sees during training, measuring the result against the 61% baseline and the 95% target); Coder review and Epic integration (building the workflow that surfaces the AI suggestion inside the coder's existing Epic interface, with each suggested code attributed to the relevant section of the physician note and flagged for coder confirmation before submission). The approach decision shapes every subproblem that follows, so address it before designing anything else.

Choosing the right approach: Why prompting hits a ceiling: the hospital's physicians write notes in documentation styles shaped by their individual training and local conventions; prompting can describe the target codes and the format they should appear in, but it cannot teach a model to recognize how a given physician phrases a specific diagnosis or how the hospital applies modifier codes across different procedure types; further prompt improvements narrow the gap incrementally but cannot close it to 95%. Why retrieval does not fit: RAG adds content retrieved from an external document corpus to the model's input; in a coding task, the physician note is already in the model's context; retrieving content from other notes or billing references does not help the model read and interpret the note in front of it; the gap is a pattern recognition problem, and retrieval does not address it. Why fine-tuning fits this case: the gap is behavioral; the base model does not know how physicians at this hospital write; that kind of pattern is learned from examples, not corrected with better instructions; labeled examples exist (the hospital has coded encounters from the past year with confirmed correct code assignments; those become the training data); HIPAA rules out commercial APIs, so the solution must run on a self-hosted open-weight model; that model scored 61% without any adaptation; fine-tuning on the hospital's own encounter history closes the documentation pattern gap and compensates for the capability difference between a self-hosted model and a commercial API.

Constraints that shape the design — three: **HIPAA requires on-premises deployment** (patient notes cannot be sent to any external API; the model, the notes, all outputs must stay within the hospital's private servers; open-weight models are the only viable foundation); **Training data quality is a prerequisite** (fine-tuning on inconsistently labeled encounters teaches the model wrong patterns; annotation guidelines and a measurement of labeler agreement must be established and verified before training data is collected); **Coder review gates every submission** (every AI-generated code set requires a coder to review and confirm it before the claim reaches the insurer; the integration surfaces a reviewable suggestion attributed to its source in the physician note, with each code flagged for coder confirmation before submission).

Refined problem statement: design a fine-tuning pipeline that trains an open-weight model on labeled coded encounters from past years, evaluates it at the code level and the claim level against a held-out test set, surfaces suggestions inside the coder's Epic workflow with each code attributed to the relevant section of the physician note and flagged for coder confirmation before the claim is submitted. A refined problem statement is the output an FDE delivers from this kind of working session with the customer; it converts an ambiguous ask into an agreed-upon scope; every design decision that follows traces back to something surfaced here, whether a constraint, a data reality, or a clarifying question that revealed a hidden assumption; that traceability is what makes the design defensible when stakeholders push back.

**Design**: the two pipelines share the adapted model as their common point; the training pipeline produces it; the inference pipeline uses it. The **training pipeline** runs on a schedule and moves through four stages: the hospital's Epic system is the source of both physician notes and confirmed code assignments; those records are extracted, cleaned, formatted as training examples; an open-weight base model is then adapted on those examples; the resulting adapter is evaluated against a held-out test set before it is promoted to the inference server. The **inference pipeline** runs each time a coder opens a new encounter: the physician note is retrieved from Epic and passed to the adapted model on the hospital's inference server; the model returns a structured code set; the result is formatted, attributed back to the relevant phrases in the note, surfaced inside the coder's Epic coding screen for review and confirmation.

Training data: the training pipeline begins with the hospital's existing coded encounter records; before any model training starts, establish what data is available and prepare it into a form the model can learn from. Extracting records from Epic: query Epic for completed encounters from the past year where a certified coder confirmed the final code assignments; each record contains two things: the full text of the physician note and the confirmed set of ICD-10 and CPT codes including any modifier codes applied; records where the code assignment was revised multiple times or flagged as disputed are excluded; such records introduce inconsistency from which a model cannot learn reliable patterns; the extraction produces a dataset where every input has exactly one verified output; that consistency is what the training step depends on. Preparing training examples: each record is formatted as a structured training example; the physician's note is the input; the confirmed code set, formatted to show ICD-10 codes, CPT codes, modifier codes in a consistent structure, is the output; annotation guidelines specify how to handle edge cases such as notes that are dictated and transcribed rather than typed, and encounters where the note and the confirmed codes come from different authors. Divide the full dataset into three non-overlapping sets before any training begins: the training set is what the model learns from; the validation set monitors training progress and signals when the model stops improving; the held-out test set is set aside at the start and never used until final evaluation. Keeping the test set locked from the beginning is the only way to produce an accuracy measurement the hospital can trust as evidence for deployment.

Model selection: select an open-weight base model before fine-tuning begins; three criteria drive that choice: **Context window length** (physician notes vary significantly in length across departments; the model must handle the longest notes in the dataset without truncating content; a truncated note produces unreliable codes because the model cannot see the full clinical picture); **Parameter count** (the model must fit within the GPU memory available on the hospital's on-premises hardware; a model that exceeds available memory cannot be deployed regardless of benchmark performance); **Instruction-following quality** (a model already trained to produce structured outputs provides a better starting point for adaptation; the fine-tuning step teaches the model this hospital's specific coding patterns; the base model supplies the general language capability those patterns build on). Open-weight instruction-tuned models such as Llama 3, Mistral, Phi-4, Gemma 2 satisfy all three criteria and deploy entirely on private infrastructure.

Fine-tuning approach: the adaptation this hospital needs is targeted; the base model already understands language and clinical documentation; what it lacks is familiarity with this hospital's specific coding patterns, and that comes from exposure to labeled examples. Fine-tuning techniques fall into several categories: **Full fine-tuning** updates every parameter in the model; **Partial fine-tuning** updates only selected layers; **Additive methods** add new trainable components on top of a frozen base model; **LoRA** (Low-Rank Adaptation) is an additive method that injects small trainable weight matrices into the model's existing attention layers and trains only those matrices while the rest of the model stays frozen. Use **QLoRA**, which combines LoRA with quantization of the base model's weights during training; quantization converts the model's high-precision weight values to a lower-precision format, reducing memory usage with minimal accuracy loss. Three properties make this the right fit: the adapter is small and stored separately from the base model; when billing guidelines change, retrain only the adapter without touching the base model; LoRA on a small dataset carries significantly lower overfitting risk than full or partial fine-tuning because far fewer parameters are updated; quantization of the base model during training reduces GPU memory requirements to a level the hospital's on-premises hardware can meet.

Evaluation: measure the adapted model across three dimensions before it moves to the inference server: **Field-level accuracy** (the percentage of individual codes the model assigns correctly across the held-out test set; measure ICD-10 codes, CPT codes, modifier codes separately; a model that performs well on diagnosis codes but poorly on modifier codes points to a specific training data or annotation problem that a single overall accuracy number would hide); **Claim-level first-pass rate** (the percentage of complete encounter code sets where every code is correct; a claim is either fully correct or it results in a denial; this is the metric that maps directly to the 95% target and to the hospital's business problem); **Baseline comparison** (the fine-tuned result is measured against three reference points: the 61% zero-shot open-weight result from the case study; a few-shot prompting baseline, where confirmed examples are added to the prompt without any training, to show how much prompting alone can contribute; the intermediate fine-tuning checkpoints, to show how much training contributed beyond prompting). Stop training when the validation set loss stops improving rather than when the training loss reaches its minimum; training past that point produces a model that memorizes the training examples rather than learning the patterns that generalize to new notes; once the evaluation confirms the model meets the target, it is promoted to the inference server.

Inference pipeline: when a coder opens an encounter in Epic, the inference pipeline runs; the physician note text is retrieved from Epic and passed to the adapted model on the hospital's inference server; the model returns a structured code set covering ICD-10 codes, CPT codes, applicable modifier codes for that encounter; before the output reaches the coder's screen, a formatting step attributes each suggested code to the specific phrase or sentence in the physician note that supports it; this attribution is what lets the coder verify a suggestion without rereading the full note; the formatted suggestion is then written back into Epic's coding screen alongside the note; the pipeline completes in seconds; the coder does not wait for inference to finish before the encounter loads; the suggestion appears as the coder begins reviewing the note.

Coder review and Epic integration: the coder review step is the point at which every AI output becomes a human-confirmed record; four requirements govern this step: every suggested code is marked as AI-generated until the coder confirms it; an unconfirmed suggestion cannot progress to the billing system; when the coder confirms a code, the confirmed assignment replaces the suggestion in the record; when the coder corrects a code, the corrected value is recorded alongside the original AI suggestion so the correction history is preserved; only the coder-confirmed code set is submitted to the billing system and used to generate the claim; every AI suggestion, every coder action, the final submitted code set are written to an append-only audit log; that log provides the traceability the hospital needs if a payer challenges a claim or a compliance review requires documentation of how a code was assigned. The suggestions surface inside the coder's existing Epic coding workflow; integration with Epic uses the platform's standard application programming interface, which the hospital's IT team already manages for other clinical integrations; no new interface is required for coders to start using the system.

Deployment: all components run on the hospital's private on-premises servers; no component makes outbound calls beyond the hospital's internal network. Component table: Training job — GPU server, batch job — runs offline on demand when billing guidelines change or enough new labeled examples accumulate to warrant a refresh. Inference server — GPU server, always-on — serves the adapted model to the Epic integration layer on demand. Epic integration layer — application server — reads notes from Epic, calls the inference server, writes suggestions back. Audit log store — append-only database — retains every AI suggestion and coder decision for compliance review. A system design grounded in the customer's actual constraints is defensible in ways a generic architecture is not; every component here exists because the case study required it; that traceability is what makes the design practical to hand off and straightforward to explain when stakeholders push back.

**Interview questions (Fine-Tuning)** — six carousel sections; only the first answer in each section was expanded and read (see README limitation). Paraphrased first answers:
- Decision making: When choose fine-tuning over prompting to close an accuracy gap? What signals tell you prompting has hit its ceiling? Three signals, appearing together, point toward fine-tuning. First, the error pattern is behavioral rather than factual; the model understands the task but does not produce the target behavior. Second, few-shot examples in the prompt improve accuracy on the demonstrated cases but do not generalize. Third, the gap between the baseline result and the target is large enough that no reasonable number of prompt iterations will close it. When those signals appear and labeled examples from the target domain exist, fine-tuning is the right call.
- Training data: How structure a training example for a structured output task where the input is a document and the output is a set of fields? Each training example needs three components: a consistent input format, a consistent output format, a consistent mapping between them. The input is the document text, cleaned and formatted the same way it will appear at inference time. Consistency between training and inference is the most important property; if the input format at inference differs, the model must generalize across a gap it was not trained for.
- Method selection: How does LoRA reduce memory usage compared to updating all model parameters? In full fine-tuning, every parameter in the model accumulates a gradient and an optimizer state during training. LoRA freezes all of the base model's parameters and adds a pair of small matrices, A and B, to specified layers; only those small matrices are trained, so the gradient + optimizer state are held only for a small fraction of the parameters, sharply reducing memory.
- Evaluation: How evaluate a fine-tuned model on a structured output task where there is both a field-level and a full-record measure? Measure both and report them separately because they answer different questions. Field-level accuracy measures the percentage of individual output fields the model gets correct; it shows where errors concentrate. Full-record accuracy measures the percentage of complete outputs where every field is correct; a record with one wrong field is a failed record. It is possible to have high field-level accuracy and low full-record accuracy if errors distribute across many records, so reporting only one hides the business impact.
- Changing requirements: If the hospital had no HIPAA restriction and could send notes to a commercial API, would fine-tuning still be the answer? Not necessarily. The HIPAA constraint forcing a self-hosted open-weight model is one of the two reasons fine-tuning was chosen; the other is the hospital-specific coding pattern gap. With a commercial API available, the right first step would be to test a strong few-shot prompt with that API, because a stronger base model may close much of the gap without training. Fine-tuning would still be the right call if the hospital's physician note style or modifier code conventions remain outside what prompting can teach.
- Role-specific: The coding director asks why we chose QLoRA over full fine-tuning; how explain the decision without technical jargon? Choose the approach that matches the size of the change actually being made. Full fine-tuning updates every part of the model, which is like renovating an entire building when only a few rooms need adjusting; it requires significantly more computing resources, takes longer, and on a dataset this size it tends to over-adapt the model to the training examples in ways that hurt performance on new, unseen notes. QLoRA makes a smaller, more targeted set of changes while leaving the rest of the model untouched; it requires less computing power, produces a model that learns the hospital's specific coding patterns without losing its general language understanding, and stores the adjustment separately from the base model; when the hospital's billing guidelines change, update only that stored adjustment rather than retraining everything from scratch.

Closing line: preparing for these questions builds something beyond recall; working through the reasoning behind each decision develops the judgment the role requires.
