# POC → Production (Modules 3–4)

> POC asks: does the approach work? Pilot asks: does a more complete version work for end users in day-to-day workflows under production-like conditions? A test set does not capture organizational fit, unexpected inputs, or trust.

## 1. The Pilot Phase

The pilot adds: broader input coverage (the full distribution including messy/unexpected inputs), live integrations (real auth, live feeds, write-back), error handling/edge logic (cases the POC left out of scope). It explicitly **excludes**: production-grade monitoring infrastructure, complete compliance/audit documentation, data-governance approvals, org-wide scaling work.

Pilot scope document: capabilities (expanded inputs/workflows), integrations, users (who, role, daily use), timeline (weeks to build, feedback cadence, readout date), success criteria across metric performance **plus** adoption **plus** trust.

Feedback cadence: weekly/bi-weekly structured check-ins plus ongoing error logging. No check-ins means feedback arrives too late.

**Shadow mode**: the AI processes the same requests in the background, outputs are not shown, the existing process drives decisions. Compare side-by-side accuracy/failure patterns. Move to an active phase once shadow outputs are consistently reliable.

Working with real users: set expectations (what it does/does not do, how to report a problem; a sub-one-hour orientation prevents over-reliance after a few wins or dismissal after a first error). Capture feedback via a form, a Slack/Teams channel, or a weekly check-in — with input + output + what was wrong (vague feedback is not actionable). Review throughout, not only at the end. Iterate within scope: in-scope improvements yes, new requirements logged/deferred. Expanding scope mid-pilot delays and distorts evaluation.

Three readiness signals:
- **Reliability** — consistent under real operations: stable latency, predictable quality across input types, no silent failures. Check distribution, not just the mean.
- **Adoption** — behavior: stop checking the manual alternative, regular usage, organizing work around outputs. Low adoption + strong metrics signals trust/usability, not technical failure.
- **Trust** — act on output vs. re-verify everything. High re-verification means low confidence even if accuracy is strong. Builds via consistent performance + absence of unexpected failures.

Example: 91% test accuracy can still fail adoption if users do not understand or trust the system, or if workflow friction blocks use.

Pilot readout: users, duration, metric results under real conditions, adoption data (usage, revert-to-manual frequency), trust signals (override rates, feedback themes), recommendation. Outcomes: **Proceed to full deployment** (all three signals positive + customer ready to operate independently — define deployment prerequisites before leaving the readout) or **Extend pilot** (one or more signals need time/intervention — define the change + timeline before the meeting ends). A rare fundamental constraint surfacing (governance, access change, org decision) → surface clearly and work a path forward.

Deployment prerequisites are **customer commitments**, not FDE deliverables: a named system owner, a support channel for users, a plan for monitoring after the FDE exits.

## 2. The Project Handoff

Handoff quality determines whether value persists after the FDE leaves. A system without documentation, monitoring, and trained owners is a dependency, not a deliverable. AI cannot be fully validated pass/fail: outputs are probabilistic, behavior shifts with input distribution, and a test suite cannot catch quality drift or latency degradation at real volume.

Five deployment-ready dimensions (agree minimum viable + target thresholds pre-handoff): Reliability (consistent, no unexpected/silent/unhandled failures; peak-load behavior characterized pre-go-live); Output quality (pilot accuracy/precision/recall holds at real volume across the full input range, not only the test set); Safety (no output type can cause downstream harm without human review; especially agentic action-taking systems); Cost (token + infra at full volume within the committed budget — cost sustainability is readiness, not post-launch); Observability (the operating team can see what is happening, catch degradation early, investigate independently).

Minimum viable deployment: agree the minimum responsible go-live threshold, not the ideal state. Usability/workflow coverage can improve post-deployment; safety + observability must meet minimums before supporting production decisions.

Handoff has four components: code, in-code documentation, a formal handoff document, a live handoff session.

Code for someone else: consistent naming, configuration separated from logic, no FDE-local-only tool dependencies, a customer-accessible repo runnable day one, comments where a choice is non-obvious, a README for setup/test.

The handoff document covers five areas: system overview (does, inputs, outputs, does not handle); data flow (sources, movement, stored, sent to external APIs); known failure modes (how, how often, triggers, in-flight requests); monitoring setup (tracked, thresholds, alert meaning); escalation path (when a human intervenes, who, expected action). Written in the customer engineering team's language — if it requires the FDE to interpret, nothing transferred.

The handoff session is a live end-to-end walkthrough (architecture, data flow, monitoring, failure modes), recorded. Goal: confirm the team can run/monitor/troubleshoot independently and knows whom to contact when beyond the runbook.

Monitor five categories: latency (per-request vs. operational requirement, peak-load/over time); error rate (timeouts, API errors, unhandled exceptions; stable vs. trending up); output quality sampling (a weekly random sample vs. pilot criteria, log deviations — catches gradual drift from new distributions/staleness before user complaints); cost per query (token costs at full volume vs. budget; an unexpected agentic cost rise often means unintended repeated tool calls); user engagement signals (continued use, override rate — a rising override rate means quality drift or new edge cases).

Human-in-the-loop fallback has three components: **trigger** (confidence below an agreed threshold, a flagged category: high-value/sensitive/unusual, or a technical failure preventing completion; agreed pre-deployment); **queue** (where flagged items go, who reviews, timeframe — no named reviewer + no SLA means not a fallback); **logging** (the reviewer decision is recorded and used in evaluation; overrides are a signal for model failure patterns).

Logging / data handling: per-request log: unique request ID, timestamp, input category/type (not the full input if sensitive), model output/output type, latency, error codes/failure signals, human-override flag. Do NOT store full user data, customer-identifying information, or complete PII-containing inputs in general logs. Debug via primary data storage under the same access controls, not indefinite log retention. Structured logging (consistent JSON, defined fields) beats free-form at scale. Agree the log schema pre-deployment and confirm the team can query it.

Post-handoff: an **internal champion** (understands the system, onboards, handles routine questions, spots the need for outside help; identify/prepare during the pilot — no champion means dependency on finding an FDE contact); a **support window** (how long the FDE is available; in-scope: build bugs, confusion about documented behavior; out-of-scope: new requirements, customer infrastructure changes, customer-chosen model updates — an undefined window means indefinite dependency). A clean exit means: handoff document complete, monitoring active, champion prepared, support window agreed, no open technical obligations.

## 3. The Field Feedback Loop

The product team does not see customer environments directly. Friction, product shortfalls, slow integrations, repeated questions are missed outside the field. The FDE is **product intelligence**: technically deep + organizationally close. Roadmaps from tickets/sales reflect what customers *say* they want; FDEs see what customers actually encounter. Accountability is two-part: deliver customer value **plus** bring field intelligence back. The second is equally important and easier to neglect. A project closing without recording learning is a missed opportunity.

Field-notes habit: a structured log as it happens, not a formal report. Capture: product gaps (pain the product does not solve, worked around/abandoned); integration friction (what took longer + the specific reason); documentation gaps (repeatedly asked, documentation did not answer); unexpected failure modes (real-use failures not in the evaluation plan); customer workarounds (invented steps compensating for a missing capability — these reveal unmet needs more clearly than feature requests). Capture in real time or immediately after a session/check-in/feedback conversation. No specific customer names, confidential business details, or identifying information. Format light/sustainable: a shared document, dated entries, tagged category, searchable/honest.

**Signal vs. noise**: most single-project observations are noise (one customer's unusual setup, one user's misconception, a one-off edge case). Treating all as product gaps wastes product-team attention and damages credibility. A signal appears across customers/industries/use cases (the same integration issue independently, the same question from unconnected customers, the same workaround independently). Two factors: the framing question ("specific to this customer, or would any customer with this setup face it?" — an unusual internal data structure is noise; a missing standard connector for a shared enterprise-tool category is a signal) and the time dimension (a pattern looks one-off at project three, a clear gap by project five; notes enable recognition). The strongest signals are seen at least twice in distinct customer contexts and are specific enough to describe the commonality.

Useful product feedback has six elements: problem observed (specific, operational context); frequency (how often, across how many customers); severity (what the customer had to do — an independent workaround means high severity); what the customer tried (approaches before the workaround, revealing expectations); what would solve it (a concrete fix from the customer perspective); estimated impact (a rough number of customers affected + business value unlocked). Example: in three of the last four projects, customer teams could not find documentation for the auth flow connecting to on-premises systems; all three created internal documentation; a structured integration guide could save roughly 2–3 days of setup per project for that segment. Present as a data point + business impact + proposed direction, not product criticism/demand (defensive vs. collaborative).

Working with internal teams: product team — the FDE is a signal source, not the customer; feedback is input with a business case, not an instruction/demand; the product team has unseen constraints/priorities. Engineering escalations: a bug mid-project needs prioritization without damaging the relationship; an effective escalation has a clear bug description, reproduction steps, customer impact in business terms, and a suggested priority + reasoning. Urgent-no-context escalations get deprioritized. Competing priorities: engineering sprints vs. FDE customer urgency rarely align; know what waits for the next release, what can be worked around at the customer level, and what genuinely needs immediate action. Over-escalating reduces the impact of real escalations.

## 4. Navigating Enterprise Constraints

An enterprise is complex organizations, not just technical systems. Treating it only as technical misses the human/organizational dynamics that determine whether work moves or stalls. Challenges appear in almost every project: data access slower than described, security changing the architecture, organizational dynamics creating non-technical friction, scope drift.

Enterprise mindset: environments rarely match descriptions/diagrams (an architecture slide's four clean systems becomes roughly twice as many in reality, with manual handoffs and unmentioned dependencies that are "just how things get done"). The productive response is curiosity, not frustration. Domain knowledge (healthcare, financial services, legal) accelerates day-one questions.

**Data access** — three challenges: getting access, working with the data once it arrives, recognizing when the data itself is the problem. Who controls access: the describer is not the controller. An executive's "we have all the data" may still require an IT security ticket + a data governance committee + a 2–3 week review. Go directly to the technical contact with specifics: systems, permissions (usually read-only), data types, the security review process. A general request via the executive chain loses detail and slows things. Sample data strategically: a scoping sample confirms format as described; a build sample must be representative of the real distribution including messy/edge cases, not only clean discovery examples. A pipeline tested only on clean examples meets real failure modes at demo. When the data is the actual problem: a system with data from the same vendor in fifteen name formats, inconsistent budget figures, and 30% of records missing required fields will be unreliable regardless of model configuration. Communicating that beats building complex preprocessing that partially compensates.

**Security / compliance** — four recurring items: data residency (data cannot leave a jurisdiction/infrastructure boundary); no-internet-egress (no outbound calls to external services); PII handling restrictions (certain fields cannot go to external model APIs); model hosting requirements (the model on the customer's own infrastructure). Each can change the architecture/deployment; discovering one in implementation costs more than in scoping. Meet IT security with specifics: what data is processed, where it is stored/transmitted, which systems handle it, access controls, what events/fields are logged. The security team manages risk, not slows the project; specific requests move faster. Three practical approaches: data anonymization (PII → synthetic equivalents, preserve structure); synthetic data for testing (same statistical properties, no real customer information, when real data is inaccessible in development); private model deployment (an open-weight model on customer infrastructure when an external API is not permitted).

**Organizational politics / champions**: projects affect people's jobs/tools/workflows. Some want success, some are indifferent, some see a threat. A champion is motivation + internal influence to clear blockers. Title is not the best indicator — a senior individual contributor who believes and has relationships across IT/operations/legal is often more useful than an absent VP who signed the budget. Value is willingness to move things. The **shadow IT** problem: a project may threaten an existing tool/process/team; a workflow owner may be built around manual work. Surface early, involve the affected team in design, frame the system as handling routine cases while the team focuses on complex ones — prevents resistance appearing as unexplained adoption friction. When a champion changes (leaves, role change, loses support): identify a replacement quickly. No champion means stalls at the first obstacle. Identify who controls each part of the environment at the start, not when a blocker appears.

When a project goes sideways — four patterns: **early warning signs** (check-ins rescheduled without rescheduling, the champion less reachable, new stakeholders appearing who were not at scoping; individually not signals, all three together usually are; early recognition creates room); **technical dead ends** (communicate a pivot before the next milestone, not at it — an early pivot is a course correction, at a demo it is a failure; frame as what was learned that changes the approach); **escalation as a skill** (resolvable via an existing channel is not escalation; needs a decision from a higher authority is escalation; escalate everything is noise; never escalate turns a solvable issue into a crisis; distinguish accurately and act before compounding); **a failed demo** (live demos fail; have a recorded backup and know what to say; acknowledge, switch to the backup, explain calmly; composure builds trust, not less). Enterprise constraints are normal conditions, not edge cases.

## 5. Communicating Across Stakeholder Types

The same update can give an engineering lead enough detail but confuse an executive or frustrate an operations manager. Four stakeholder types: executive sponsor (ROI, organizational risk, competitive position, timeline; business outcome over technical approach); technical lead (architectural soundness, integration complexity, can their team maintain it); end user (does it make the actual job easier/harder; pilot behavior is the most honest adoption signal); procurement/legal (compliance, liability, contract terms accounting for AI decision risks).

Principle across all: **lead with outcomes, follow with mechanisms**. The audience determines which outcomes matter.

Executives: lead with a business translation, not architecture/accuracy percentages. E.g., retrieval + reranking means contract review from three hours to twelve minutes. Find the translation before the meeting. Skepticism is met with specificity over enthusiasm. Show measured results vs. the agreed success criterion over optimistic framing. An executive update has four parts: **Situation** (current state), **Recommendation** (proposed next step), **Impact** (what the action means for the project/organization), **Ask** (what is needed from the executive).

Engineers: technical credibility is non-negotiable, tested early/deliberately, and remembered. It builds via precise technical talk, honestly acknowledging real tradeoffs, and asking questions showing familiarity with the customer team's constraints. Architecture conversations: present decisions with reasoning, not just conclusions; explain why a pattern was chosen + alternatives ruled out → collaboration, not defensiveness. Code in the customer environment will be read/maintained by their team: clear naming + configuration/logic separation signals judgment.

Communicating AI capability honestly: overpromising is the most consistent trust damage. Executives under pressure amplify optimistic statements to boards; when they do not materialize, the FDE + the project lose credibility. Frame honestly: a system handling 85% autonomously and routing 15% to a human is still an improvement over today at 100% manual review. Confidence thresholds define act vs. escalate; define them during scoping, not after an incident.

"Can you guarantee the system will not produce incorrect outputs?" — a useful answer has three parts: how low-confidence outputs are handled; what human review looks like + who owns it; how errors are caught before becoming decisions the organization must reverse. The customer wants risk management, not a guarantee.

Written artifacts build trust: written outlasts verbal. A stakeholder who forgets a meeting remembers a saved status update. Document quality signals engineering quality. Five documents in sequence: discovery notes (problem, data, stakeholders, constraints); scope document (what is built, success criteria, explicit out of scope); weekly status updates (completed, blocked, planned, needed from the customer); POC readout (built, measured, measurement showed, recommendation); handoff document (system overview, data flow, known failure modes, monitoring, escalation). Together they form a written record serving the customer team long after the FDE leaves.

## Self-test (4 questions)
1. A pilot shows 91% accuracy but users keep checking the manual process. Which readiness signal is failing, and what does it mean?
   → Adoption (or Trust). Low adoption + strong metrics signals trust/usability, not technical failure.
2. What are the four components of a handoff, and what makes a "clean exit"?
   → Code, in-code documentation, formal handoff document, live handoff session. Clean exit: handoff doc complete, monitoring active, champion prepared, support window agreed, no open technical obligations.
3. How do you tell a signal from noise in field feedback?
   → A signal appears across customers/industries/use cases (same issue/workaround independently), seen at least twice in distinct contexts, specific enough to describe the commonality. Single-project observations are usually noise.
4. An executive asks "can you guarantee no incorrect outputs?" What is the useful answer structure?
   → How low-confidence outputs are handled; what human review looks like + who owns it; how errors are caught before becoming decisions the organization must reverse. Risk management, not a guarantee.
